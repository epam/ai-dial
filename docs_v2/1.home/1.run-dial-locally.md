# Run DIAL locally

In this tutorial, you will run the full DIAL platform on your own machine with Docker Compose — DIAL Core, DIAL Chat, DIAL Admin, and Keycloak for authentication. By the end, you will sign in as a real user, chat with a model, and open the Admin console. This is a production-like stack, not a toy setup, so you will need credentials for at least one language model.

:::tip
Just want to look, not install anything? Try the hosted [DIAL SaaS edition](https://chat.dialx.ai/) in your browser instead.
:::

## Prerequisites

- Docker Engine with Docker Compose v2.20.0 or higher. See the [Docker documentation](https://docs.docker.com/desktop/).
- An endpoint and API key for at least one language model — an Azure OpenAI deployment, another DIAL instance, or an Anthropic API key. The stack ships with placeholder credentials and cannot answer prompts until you supply real ones.
- Free TCP ports `3100` (DIAL Chat), `3101` (themes), `3102` (DIAL Admin), and `8900` (Keycloak).

## What you'll build

The eight-service stack defined in [`dial-docker-compose-advanced/dial-2.x/`](https://github.com/epam/ai-dial/tree/main/dial-docker-compose-advanced/dial-2.x): DIAL Core, DIAL Chat, DIAL Admin (backend and frontend), Keycloak, Redis, a themes server, and the OpenAI adapter. Unlike a minimal setup, this one has real authentication and a working Admin console, which is what makes it a useful local mirror of a deployed DIAL.

## Step 1: Get the Docker Compose files

Clone the repository and change into the DIAL 2.x advanced setup:

```bash
git clone https://github.com/epam/ai-dial.git
cd ai-dial/dial-docker-compose-advanced/dial-2.x
```

**Verify:** the folder contains `docker-compose-base.yml`, `docker-compose-full.yml`, a `.env` file, and a `core/` directory.

## Step 2: Add your model credentials

Open `core/config.json`. The `models` section ships with placeholder upstreams that must be replaced — for example, `gpt-5`:

```json
"upstreams": [
    {
        "endpoint": "http://azure_or_dial_deployment_host/openai/deployments/gpt-5/chat/completions",
        "key": "AZURE_MODEL_OR_DIAL_API_KEY"
    }
]
```

Replace `azure_or_dial_deployment_host` with your model host and `AZURE_MODEL_OR_DIAL_API_KEY` with your key. You only need to fix one model to finish this tutorial; delete or ignore the others for now. For the pre-configured `claude-sonnet-4-5-20250929` model, supply an Anthropic API key instead.

**Verify:** no `azure_or_dial_deployment_host` or `AZURE_MODEL_OR_DIAL_API_KEY` placeholder remains in the model you intend to use.

## Step 3: Start the stack

```bash
docker compose -f docker-compose-base.yml up
```

Docker pulls eight images and starts them in dependency order. The first run takes several minutes while images download.

To also run DIAL RAG for document question-answering, use `docker compose -f docker-compose-full.yml up` instead.

**Verify:** the logs settle with no restart loops, and Keycloak reports itself healthy.

## Step 4: Sign in to DIAL Chat

Open `http://localhost:3100` and sign in through Keycloak. The realm ships with three pre-defined users, all with the password `dial`:

| Username | Password | Access |
|---|---|---|
| `user` | `dial` | Basic access to DIAL Chat |
| `dial` | `dial` | Admin access to DIAL Chat |
| `dial-admin` | `dial` | Access to the DIAL Admin console |

Sign in as `dial`.

**Verify:** DIAL Chat loads with your username visible, having redirected you through Keycloak rather than straight into the UI.

## Step 5: Chat with a model

1. In the message box, click the model dropdown in its bottom-right corner (it shows the currently selected model's initials).
2. Type a prompt in the chat box and send it.

**Verify:** the model replies. If you get an upstream error instead, check the model's upstream endpoint and key in the Admin console (Step 6) and correct them there.

## Step 6: Open the Admin console

Sign out, then open `http://localhost:3102` and sign in as `dial-admin` with the password `dial`.

To find the models you configured by hand in Step 2, open **Entities → Models** in the left navigation. The grid lists every model registered in `config.json`, with its ID, display name, and source type.

Click a model to open its configuration screen. Under **Properties → Upstream configuration** are the **Chat completion endpoint** and **Keys** fields — the same upstream endpoint and API key you typed into the file in Step 2, now editable through the UI. Changing them here and clicking **Save** rewrites the same configuration. To register a model that is not listed yet, click **+ Create** on the Models screen.

**Verify:** the Models grid lists the model you chatted with in Step 5, and its upstream endpoint matches what you put in `core/config.json`.

## How it fits together

You signed in as two different users and got two different levels of access. That is what separates this stack from a demo setup: the authentication is real. Keycloak holds the accounts and issues a signed token when you sign in, and DIAL Core reads the roles in that token to decide what you are allowed to call — which is why `dial-admin` can open the Admin console and `user` cannot. A deployed DIAL works the same way, with your organization's identity provider in place of Keycloak. See [Authentication](../4.operating-dial/4.configuration/9.docker-compose/2.advanced/2.auth.md) for the configuration behind this.
