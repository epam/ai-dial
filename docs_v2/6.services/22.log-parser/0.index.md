# DIAL Log Parser

DIAL Log Parser converts DIAL Core request logs into Parquet datasets partitioned by deployment and date. This reference is for platform engineers with existing Core log files and writable dataset storage. The output supports offline analysis and evaluation.

:::info

- [Repository](https://github.com/epam/ai-dial-log-parser)
- [Releases](https://github.com/epam/ai-dial-log-parser/releases)
- [Docker Hub image tags](https://hub.docker.com/r/epam/ai-dial-log-parser/tags)

:::

## How parsing works

```mermaid
flowchart LR
    Core[DIAL Core] --> Logs[Stored request logs]
    Logs -->|one selected date| Parser[DIAL Log Parser job]
    Parser -->|deployment and date partitions| Parquet[Parquet dataset]
    Parquet --> Analysis[Offline analysis or evaluation]

    classDef coreStyle fill:#dbeafe,stroke:#2563eb,color:#1e3a8a;
    classDef processingStyle fill:#f3e8ff,stroke:#9333ea,color:#581c87;
    classDef storageStyle fill:#fef3c7,stroke:#d97706,color:#78350f;
    classDef extStyle fill:#e5e7eb,stroke:#6b7280,color:#374151;
    class Core coreStyle;
    class Parser processingStyle;
    class Logs,Parquet storageStyle;
    class Analysis extStyle;
```

The parser recursively lists the input directory, matches file names, and selects files for one date. It normalizes request records and writes deployment/date partitions. The [implementation](https://github.com/epam/ai-dial-log-parser/blob/0.3.0/src/aidial_log_parser/parse_logs.py#L167-L179) derives the partition date from the filename, rather than the request timestamp.

An existing `deployment` field is retained. When absent, the parser extracts it from `/openai/deployments/<DEPLOYMENT>/chat/completions` or `/openai/deployments/<DEPLOYMENT>/embeddings`. Rows without a deployment are removed, and invalid Arrow batches are skipped with logging. See [batch processing](https://github.com/epam/ai-dial-log-parser/blob/0.3.0/src/aidial_log_parser/parse_logs.py#L335-L368).

Log Parser is a finite batch job, with no HTTP port or health endpoint. Scheduling belongs to the deployment's job scheduler. It writes Parquet rather than populating [DIAL Analytics](../20.analytics/0.index.md), whose own ingestion reads raw logs into ClickHouse. The [Enrichment Runner](../21.analytics-enrichment-runner/0.index.md) does not consume this dataset as its pipeline input.

## Output schema

The [Arrow schema](https://github.com/epam/ai-dial-log-parser/blob/0.3.0/src/aidial_log_parser/parse_logs.py#L30-L124) defines the output fields. Other raw-log fields are not part of the declared output schema.

| Field | Type and content |
|---|---|
| `deployment` | String partition key, stored in the directory path |
| `date` | `date32` partition key, from the log filename |
| `apiType` | Nullable string identifying the API type |
| `chat` | Nullable struct containing string `id` |
| `project` | Nullable struct containing string `id` |
| `user` | Nullable struct containing string `id` and `title` |
| `token_usage` | Nullable struct: integer `completion_tokens`, `prompt_tokens`, and `total_tokens`; floating-point `deployment_price` and `price` |
| `execution_path` | Nullable list of strings |
| `trace` | Nullable struct containing string `trace_id`, `core_span_id`, and `core_parent_span_id` |
| `request` | Nullable struct containing string `protocol`, `method`, `uri`, `time`, and `body` |
| `response` | Nullable struct containing string `status`, `upstream_uri`, and `body` |
| `assembled_response` | Nullable JSON string, including an assembled streaming response when present in the source |
| `question` | Nullable string from the final message, only when that message has role `user` and string content |
| `answer` | Nullable value from the first response choice's `message.content` |

Missing schema fields are filled with nulls. Invalid JSON in request bodies or assembled responses produces a warning and a null extracted value. A non-object response root also yields a null answer. See [question and answer extraction](https://github.com/epam/ai-dial-log-parser/blob/0.3.0/src/aidial_log_parser/parse_logs.py#L266-L332).

**Note**
> The upstream README calls the partition field `deployment_name`. The code writes `deployment`; dataset readers must use that name.

## Dependencies and deployment

| Dependency | Purpose |
|---|---|
| Stored DIAL Core logs | Input JSON records in filenames matching the configured pattern; gzip files are supported |
| Input storage access | Read and list access to local files or the configured filesystem backend |
| Output storage access | Write access, plus deletion rights for partitions replaced during a rerun |
| External scheduler | Optional recurring execution; the image processes one date and exits |

The image is `epam/ai-dial-log-parser`. Its [Dockerfile](https://github.com/epam/ai-dial-log-parser/blob/0.3.0/Dockerfile#L22-L37) uses Python 3.12 and runs as `appuser`, UID `1001`. The [package dependencies](https://github.com/epam/ai-dial-log-parser/blob/0.3.0/pyproject.toml#L14-L19) include fsspec, PyArrow, and S3 support. Other filesystem protocols require their implementation to be available in the runtime image.

Configuration, container examples, rerun behavior, and dataset verification are in [Configuration](1.configuration.md).

**Warning**
> Output contains request and response bodies and can include personal data. Restrict dataset access and retention independently of the source logs.
> Reruns replace matching output partitions without a transactional rollback; keep source logs available for recovery.
