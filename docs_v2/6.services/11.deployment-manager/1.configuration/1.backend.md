# DIAL Deployment Manager Backend configuration

Deployment Manager Backend configures cluster access, image builds, workload lifecycles, storage, and authentication through Spring Boot properties and environment variables. This reference is for platform engineers who deploy the backend. For the settings on DIAL Admin and in the cluster, start with [Configuration overview](0.index.md).

## Version scope

Defaults below are checked against [Backend 0.22.0 `application.yml`](https://github.com/epam/ai-dial-admin-deployment-manager-backend/blob/0.22.0/src/main/resources/application.yml), with behavior described in that release's [configuration reference](https://github.com/epam/ai-dial-admin-deployment-manager-backend/blob/0.22.0/docs/configuration.md). The YAML is authoritative where its defaults differ from the reference tables: for example, Knative startup is `60` seconds and informer resync is `600` seconds.

The [development reference](https://github.com/epam/ai-dial-admin-deployment-manager-backend/blob/development/docs/configuration.md) is newer than this release and removes the NIM configuration. The 0.22.0 reference table lists KServe's informer interval as `K8S_NIM_DEPLOYMENT_INFORMER_RESYNC_INTERVAL_SEC`, but the released YAML reads `K8S_KSERVE_DEPLOYMENT_INFORMER_RESYNC_INTERVAL_SEC`; the tables below follow the YAML.

## Spring configuration

Environment variables, external YAML/properties, command-line arguments, and Java system properties can supply configuration. `SPRING_CONFIG_ADDITIONAL_LOCATION=file:/config/override.yml` adds an external file. Normal Spring precedence applies; external files do not override higher-priority environment variables or command-line options.

Full Kubernetes templates can be overridden through Spring configuration, including service accounts, pod security, volumes, annotations, and resource defaults. For example:

```yaml
app:
  knative-service-config:
    spec:
      template:
        spec:
          serviceAccountName: managed-workload
          automountServiceAccountToken: false
```

### Identity providers

Configure one or more named providers. The table uses property names; environment equivalents follow Spring binding, for example `PROVIDERS_KEYCLOAK_ISSUER`, `PROVIDERS_KEYCLOAK_JWKSETURI`, and `PROVIDERS_KEYCLOAK_ROLECLAIMS`.

| Property | Description |
|---|---|
| `providers.<name>.issuer` | Accepted issuer(s), matching the token's `iss`. |
| `providers.<name>.jwk-set-uri` | JWKS URL for signature validation. |
| `providers.<name>.user-info-endpoint` | User-info endpoint for opaque tokens, as an alternative to JWKS validation. |
| `providers.<name>.audiences` | Accepted `aud` values. |
| `providers.<name>.role-claims` | Comma-separated claim paths from which roles are read. |
| `providers.<name>.roles-mapping` | Provider-specific role mapping, merged with defaults; the provider wins for overlapping keys. |
| `providers.<name>.principal-claim` | Override the principal claim for this provider. |
| `providers.<name>.email-claims` | Email claim paths; used by providers that require them, such as GCP. |
| `providers.<name>.aliases` | Azure issuer aliases. |

Without an effective role mapping, authenticated requests are denied with `403`. See the [OIDC example](0.index.md#oidc-example) for a Keycloak configuration aligned with Admin.

### API-key authentication

API-key authentication is optional and requires OIDC security mode. The backend validates an `Api-Key` header through Core's `GET /v1/user/info`. It does not maintain its own store of API keys.

| Variable | Default | Description |
|---|---|---|
| `API_KEY_ENABLED` | `false` | Accept Core API keys alongside OIDC tokens. |
| `API_KEY_CORE_URL` | — | Required Core base URL when enabled. |
| `API_KEY_CACHE_TTL_SECONDS` | `60` | Cache lifetime for successful introspection. Revocation can take up to this interval to be observed. |
| `API_KEY_CACHE_MAX_SIZE` | `10000` | Maximum cached introspection results. |
| `API_KEY_REQUEST_TIMEOUT_MS` | `3000` | Core introspection timeout, in milliseconds. |
| `API_KEY_ROLES_MAPPING` | — | Maps project-key roles to backend roles. |
| `API_KEY_STARTUP_PROBE` | `true` | Probe Core at startup; unreachable Core aborts startup. |

Project-key callers use `API_KEY_ROLES_MAPPING`. JWT-rooted per-request keys use the default OIDC role, principal, and email mappings instead. At least one of those role mappings must be nonempty. When both `Authorization` and `Api-Key` are present, the token path takes precedence.

Core non-success responses and malformed user-info responses become `401`; transport failures become `503`. Failures are not cached. See the upstream [API-key reference](https://github.com/epam/ai-dial-admin-deployment-manager-backend/blob/0.22.0/docs/configuration.md#api-key-authentication-configuration) for the two response shapes and mapping examples.

Standard Spring datasource properties can override the generated JDBC URL. Migration locations are selected from `datasource.vendor`; the `DB_VENDOR` name in the upstream documentation table is not used by the 0.22.0 YAML.

### Private Git repositories

Entries use `host` and optional `path` to scope credentials. HTTPS/HTTP credentials use `user` and `token`; SSH credentials use `sshKeyPath` and `sshKnownHostsPath`, with files mounted into the backend. Store credential values in secrets, for example Helm `manager.secrets`.

```json
[
  {"host":"git.example.com","path":"team/service-a","user":"builder","token":"<REPOSITORY_TOKEN>"},
  {"host":"git.example.com","path":"team","user":"builder","token":"<GROUP_TOKEN>"}
]
```

An exact host wins over parent domains, then the longest matching host wins. Within that host, an exact repository path wins over a group prefix, which wins over a host-wide credential. Host matching is case-insensitive; paths are case-sensitive. Duplicate `(host, path, authentication type)` scopes fail startup in 0.21.0 and later. See [Backend 0.21.0](https://github.com/epam/ai-dial-admin-deployment-manager-backend/releases/tag/0.21.0).

### Node pools

| Variable | Default | Description |
|---|---|---|
| `NODE_POOLS` | Empty | YAML list of scheduling presets. |
| `NODE_POOL_DEFAULT` | Empty | Default pool ID for new deployments. |
| `NODE_POOL_DEFAULT_MODEL` | Empty | Model-serving default pool ID; takes precedence over the catch-all default. |

Each entry needs a unique immutable `id` and display `name`. Optional `description`, `nodeSelector`, `affinity`, and `tolerations` describe scheduling. Selectors and affinity replace template values; tolerations append to existing values. These are scheduling presets for existing Kubernetes nodes, not a node-provisioning service.

```yaml
- id: cpu-pool
  name: CPU pool
  nodeSelector:
    workload: cpu
- id: gpu-pool
  name: GPU pool
  nodeSelector:
    workload: gpu
  tolerations:
    - key: dedicated
      operator: Equal
      value: gpu
      effect: NoSchedule
```

Defaults are persisted when a deployment is created. Changing a default does not migrate existing deployments. Changing a pool's scheduling fields affects deployments using it on their next redeploy; changing its display name is safe. Renaming its `id` breaks references. The old `NODE_POOL_LABEL_KEY` has no effect.

### Network policy

`CILIUM_NETWORK_POLICIES_ENABLED` defaults to `false`. When enabled, the backend creates Cilium policies for build jobs and workloads using configured global and per-image/per-container domain rules. Cilium must be installed and the backend must have policy RBAC. UI domain lists alone do not enable enforcement. See the upstream [Cilium deployment guide](https://github.com/epam/ai-dial-admin-deployment-manager-backend/blob/0.22.0/docs/deployment_guide_full_security_model.md#4-cilium-network-policy-rbac-optional).

| `APP_LOG_LEVEL`, `SPRING_SECURITY_LOG_LEVEL`, `HIBERNATE_SQL_LOG_LEVEL`, `HIBERNATE_BINDER_LOG_LEVEL` | `INFO` | Application, security, SQL, and binder log levels. |
| `TOMCAT_ACCESSLOG_ENABLED` | `false` | Enable Tomcat access logs; pattern is configurable with `server.tomcat.accesslog.pattern`. |
| `LOG_CONFIG_PATH`, `LOG_CONFIG_INTERVAL` | `log-config/logging.levels.json`, `10` | Dynamic logger configuration path and poll interval, in seconds. |
| `CUSTOMIZABLE_TRACE_INTERCEPTOR_ENABLED` | `true` | Enable method execution logging. |
| `CUSTOMIZABLE_TRACE_INTERCEPTOR_ENTER_MESSAGE`, `CUSTOMIZABLE_INTERCEPTOR_EXIT_MESSAGE`, `CUSTOMIZABLE_TRACE_INTERCEPTOR_EXCEPTION_MESSAGE` | Release YAML templates | Entry/exit/exception log templates; the exit variable intentionally lacks `TRACE` in its name. |
| `DEBUG_OPTS` | Empty | JVM options passed by the container entrypoint. |

When trace context is available, the backend returns a W3C `traceparent` response header for request correlation. This is distinct from the workload metrics endpoint and Admin Frontend's Node.js telemetry.

### OpenTelemetry

Spring Boot 4 provides the backend's OpenTelemetry integration. Prometheus remains available independently of OTLP export.

| Variable | Default | Description |
|---|---|---|
| `OTEL_EXPORT_ENABLED` | `false` | Default for all OTLP signal switches. |
| `OTEL_TRACES_EXPORT_ENABLED`, `OTEL_LOGS_EXPORT_ENABLED`, `OTEL_METRICS_EXPORT_ENABLED` | Value of `OTEL_EXPORT_ENABLED` | Enable each signal independently. |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://localhost:4318` | Collector base URL without trailing slash; signal paths are appended. |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`, `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` | Base URL + `/v1/traces`, `/v1/logs`, `/v1/metrics` | Full per-signal URL overrides. |
| `OTEL_EXPORTER_OTLP_TRANSPORT` | `http` | `http` or `grpc` for traces/logs. Metrics always use HTTP. |
| `OTEL_TRACES_SAMPLING_PROBABILITY` | `1.0` | Parent-based trace sampling probability, from `0` to `1`. |
| `OTEL_SERVICE_NAME` | `dial-deployment-manager-backend` | Telemetry service name. |
| `OTEL_RESOURCE_ATTRIBUTES` | — | Additional resource attributes. Use `OTEL_SERVICE_NAME` for the service name. |

```bash
OTEL_EXPORT_ENABLED=true
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318
OTEL_EXPORTER_OTLP_TRANSPORT=http
```

With gRPC traces/logs, use the collector's gRPC endpoint and separately set the full HTTP metrics URL or disable metrics export. Older `OTEL_SDK_DISABLED`, `OTEL_*_EXPORTER`, `OTEL_EXPORTER_OTLP_PROTOCOL`, and `OTEL_EXPORTER_OTLP_HEADERS` settings do not configure this integration. Collector authentication headers require the Spring per-signal `headers` properties documented [upstream](https://github.com/epam/ai-dial-admin-deployment-manager-backend/blob/0.22.0/docs/configuration.md#opentelemetry-configuration).
