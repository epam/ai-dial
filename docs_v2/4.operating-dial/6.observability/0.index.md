# Observability

This page explains how observability works in DIAL: what the platform emits, how telemetry flows from components to your backends, and the two distinct observability planes you operate. It is for DevOps and platform engineers who want to understand the model before configuring tracing, metrics, logging, or analytics. No setup instructions are here — each how-to in this section covers one task.

## OpenTelemetry as the common layer

DIAL standardizes on [OpenTelemetry](https://opentelemetry.io/) (OTEL), a vendor-agnostic specification for traces, metrics, and logs. Components export telemetry over the OTLP protocol to a collector, which forwards it to whatever backend you run. Because the wire format is standard, you choose the backend — Prometheus, Jaeger, Grafana, and similar tools all consume the same data without DIAL locking you to one vendor.

OTEL gives DIAL three signal types:

- **Traces** — the path of a request as it moves across components, with parent and child spans.
- **Metrics** — numeric time series such as request counts, latency, and JVM or system resource usage.
- **Logs** — structured event records, optionally correlated with traces.

## Two observability planes

DIAL observability splits into two planes that you configure and operate independently. Keeping them separate is the key to reasoning about the platform.

```mermaid
flowchart TB
  subgraph Runtime["Runtime health (OpenTelemetry)"]
    direction LR
    Comp[DIAL components] -->|OTLP traces, metrics, logs| Collector[OTEL Collector]
    Comp -->|"scrape :9464/metrics"| Prom[(Prometheus)]
    Collector --> Backend[Tracing / metrics backend]
    Prom --> Graf1[Grafana]
  end
  subgraph Usage["Usage analytics"]
    direction LR
    Core[DIAL Core] -->|usage logs| Blob[(Blob storage)]
    Blob -->|ingest| ADAS[DIAL Analytics]
    ADAS --> CH[(ClickHouse)]
    Clients[DIAL Admin and Grafana] -->|queries| ADAS
  end
  Runtime -. "trace_id / span_id" .-> Usage
```

**Runtime health** answers "is the platform healthy?" It is the OTEL plane: components emit traces, metrics, and logs over OTLP, and a collector forwards them to your chosen backend. Prometheus metrics travel a separate, independent path — components also expose a Prometheus-format `/metrics` endpoint that Prometheus scrapes directly, without going through the collector. Use it for latency, error rates, resource pressure, and request flow.

**Usage analytics** answers "how is the platform being used, and what does it cost?" It is a separate pipeline: DIAL Core's request logs reach blob storage through a [log sink you configure](3.logging.md#send-usage-logs-to-blob-storage), and [DIAL Analytics](../../6.services/20.analytics/0.index.md) ingests them into ClickHouse. It records token counts, cost, latency, and ratings per request, and serves them to [DIAL Admin](../../5.administering-dial-new/5.analytics/0.index.md) and to BI tools such as Grafana. The optional [Enrichment Runner](../../6.services/21.analytics-enrichment-runner/0.index.md) adds derived values, and [DIAL Log Parser](../../6.services/22.log-parser/0.index.md) converts the same logs to Parquet for offline analysis.

The two planes share only one link: the OpenTelemetry `trace_id` and `core_span_id` that DIAL Analytics stores with each usage row, so a usage entry can be traced back to its request spans.

## What each component emits

| Component | OTLP (traces, metrics, logs) | Prometheus metrics | How it is instrumented |
|-----------|--------------------------------------|----------------------------------------|------------------------|
| DIAL Core | Yes (JVM and HTTP metrics, structured logs, and spans carrying `trace_id`, `core_span_id`, `core_parent_span_id`, and an `execution_path` call stack) | Yes | OpenTelemetry Java agent attached at the JVM level |
| DIAL Chat | Yes | Yes | OpenTelemetry Node.js SDK |
| [DIAL Admin Frontend](../../6.services/9.admin/0.index.md) | Yes (traces and logs; metrics when configured for OTLP) | Yes, by default | OpenTelemetry Node.js SDK; see [Admin telemetry settings](../../6.services/9.admin/2.configuration/1.frontend.md#opentelemetry) |
| [DIAL Deployment Manager Backend](../../6.services/11.deployment-manager/0.index.md) | Optional; export is off by default | Yes, `/actuator/prometheus` on port `9464` | Spring Boot OpenTelemetry integration; see [Backend observability](../../6.services/11.deployment-manager/1.configuration/1.backend.md#backend-observability). Managed workload metrics use a separate API. |
| Adapters and Applications | Yes, including system CPU and memory metrics | Yes | [DIAL SDK telemetry](../../3.building-with-dial/6.developer-tools/1.sdk-reference/4.telemetry.md) (Python) |
| [DIAL Analytics](../../6.services/20.analytics/0.index.md) | Optional; export is off by default | Yes, `/actuator/prometheus` on the API port, or on `MANAGEMENT_SERVER_PORT` when set | Spring Boot OpenTelemetry integration; see [Security and observability](../../6.services/20.analytics/1.configuration/2.security-and-observability.md#opentelemetry) |
| [DIAL Analytics Enrichment Runner](../../6.services/21.analytics-enrichment-runner/0.index.md) | Optional; export is off by default | Yes, `/actuator/prometheus` on the API port | Spring Boot OpenTelemetry integration; see [Security and observability](../../6.services/21.analytics-enrichment-runner/1.configuration/2.security-and-observability.md#opentelemetry) |

Other applications built on the DIAL SDK emit the same OTLP and Prometheus signals as any SDK-based adapter or application.

DIAL Admin's [Analytics screens](../../5.administering-dial-new/5.analytics/0.index.md) read the usage-analytics plane through DIAL Analytics, with optional enrichment processing. Configure their connection through
[DIAL Admin analytics settings](../../6.services/9.admin/2.configuration/1.frontend.md#analytics).

:::note
DIAL Core is a Java service. It does not instrument itself in application code — its traces and metrics come from the OpenTelemetry Java agent attached to the JVM. The OTEL environment variables documented in this section configure that agent; how the agent jar is attached is set at the image or JVM level, not in `config.json`. Confirm the attachment mechanism against your own deployment.
:::

:::note
Export to your chosen telemetry backend requires configuration on each component. Admin Frontend
initializes its Node.js instrumentation and serves Prometheus metrics by default. The Vector log
sidecar prints to standard output until you configure a sink. Each how-to describes what to connect.
:::

For a Kubernetes example that connects both observability planes, follow [Observability with Grafana and Prometheus](5.providers/1.grafana-prometheus.md).
