# Builders

**Builders** are reusable blueprints that administrators register once and then use to produce the
deployable **entities** that end users and applications consume. A Builder is not something an end
user interacts with directly — it defines *how* a whole class of entity is created, configured, and
run. You register the blueprint in one place, then stamp any number of concrete entities from it.

DIAL Admin has three Builder types, each paired with the entity it produces:

| Builder | What it defines | Produces |
|---------|-----------------|----------|
| **Application Runner** | An application *factory*: a JSON configuration schema plus the chat/MCP endpoints that DIAL Core calls. End users create logical app instances from it, each with its own configuration. | [Applications](../2.entities/2.applications.md) (and [public-folder Applications](../4.assets/1.applications.md)) |
| **Interceptor Template** | A reusable configuration blueprint for interceptors — the endpoints and schema that interceptor instances inherit. | [Interceptors](../2.entities/4.interceptors.md) |
| **Adapter** | The bridge that unifies a provider-specific model API (Azure OpenAI, Vertex AI, Bedrock, …) with the DIAL Core Unified Protocol. | [Models](../2.entities/1.models.md) |

## How Builders relate to Entities

Think of a Builder as the mold and an Entity as the casting. The Builder carries the shared
definition — schema, endpoints, behavior — and every entity created from it inherits that
definition. For example, Quick Apps, Code Apps, and Mind Maps are Application Runners shipped with
DIAL out of the box; each Quick App a user creates is an Application stamped from the Quick App
runner. Changing the Builder affects every entity built from it, which is what makes Builders the
right place to standardize configuration across many deployments.

Because of this dependency, deleting a Builder also deletes the entities still bound to it — removing
an Application Runner removes its Applications, an Adapter removes its Models, and an Interceptor
Template removes its Interceptors.

## What you can do here

- **[Application Runners](1.application-runners.md)** — register and configure application factories,
  including their parameter schema, features, interceptors, and app routes.
- **[Interceptor Templates](2.interceptor-templates.md)** — create reusable interceptor blueprints and
  spin up interceptor instances from them.
- **[Adapters](3.adapters.md)** — register model adapters and attach the models each one serves.

## Where Builders live in the Admin Panel

Builders are grouped under **Builders** in the DIAL Admin left menu, directly below **Entities**.
Creating entities from a Builder is done from the Builder's own configuration screen (for example,
**Create Model** on an adapter, or **Create Interceptor** on an interceptor template).
