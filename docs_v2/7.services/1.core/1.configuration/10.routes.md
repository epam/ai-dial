# Routes

A **route** publishes an HTTP or WebSocket API of your own through DIAL Core. Core matches a request's path and method to the route, authenticates and authorizes the caller, and proxies the request to the route's upstreams with load balancing. Clients such as DIAL Chat can then call the API with their DIAL credentials. This reference is for platform engineers who expose custom APIs; it assumes you know [how DIAL Core is configured](0.index.md).

For when to use a route instead of an application or a toolset, see [Custom APIs through routes](../../../2.understand-dial/3.capabilities/6.tools-and-enterprise-data.md#custom-apis-through-routes).

## Where routes are defined

| Source | Location |
|---|---|
| Config file | `routes.<name>`, for global routes |
| Configuration API | `/v1/routes/platform/<name>` |
| An application | `applications.<name>.routes`, see [Application routes](7.applications.md#application-routes) |

Routes are matched by their paths, not their names, so a file route and a blob route with the same name both stay in force. Built-in DIAL Core endpoints are selected before global routes. DIAL Admin manages routes in [Routes](../../../6.administering-dial-new/1.ai-gateway/4.routes.md).

## Fields

| Field | Description |
|---|---|
| `paths` | Regular expressions matched against the entire request path. An empty list matches every path reaching the route handler. |
| `methods` | HTTP method names the route accepts. DIAL Admin offers `GET`, `POST`, `PUT`, `DELETE`, `HEAD`, and `PATCH`. An empty list matches every method reaching the route handler. |
| `rewritePath` | When `true`, the upstream path is replaced with the path of the original request. |
| `userRoles` | Roles from identity provider claims or API keys that may call the route. When unset, the route applies no role restriction; an empty list grants access to no roles. Other access checks still apply. |
| `order` | The priority among global routes; a lower value wins. Cannot be negative. Default `2147483647`. |
| `upstreams` | The servers the route proxies to. See [Upstreams](#upstreams). Set `upstreams` or `response`. |
| `response` | A fixed response Core returns without contacting an upstream, with `status` and `body`. Caller access and rate-limit checks still apply. Set `upstreams` or `response`. |
| `maxRetryAttempts` | The maximum number of attempts per request, including the first. Default `1` means no retry. HTTP routes can retry a `429` response or a connection or send failure; WebSocket routes can retry a connection failure. Attempts are capped by the number of upstreams. |
| `attachmentPaths` | Request and response JSON paths for attachment handling on application routes. Core 0.50.1 does not process them on global routes. |

### Upstreams

| Field | Default | Description |
|---|---|---|
| `endpoint` | — | The backend URL: `http://`, `https://`, `ws://`, or `wss://`. Routes support HTTP and WebSocket. |
| `key` | — | The API key, token, or credential sent to the upstream. If unset on a proxied request, Core sends a generated per-request DIAL key in `API-KEY`. |
| `authType` | `API_KEY` | How `key` is sent on global routes: `API_KEY` as `API-KEY: <key>`, `BEARER` as `Authorization: Bearer <key>`, or `CUSTOM_HEADER` in the configured header. Bearer and custom-header authentication require a key. For a custom header, use an object such as `{"type":"CUSTOM_HEADER","headerName":"X-Api-Token"}` with a valid HTTP header name. Application routes ignore `authType`. |
| `weight` | `1` | The upstream's share of traffic within its tier. `0` or below takes it out of routing. |
| `tier` | `0` | The priority group; the lowest value is used first. |
| `baseUrl` | — | Accepted in the upstream configuration, but Core 0.50.1 global-route forwarding uses `endpoint` rather than this field. |
| `extraData`, `secretExtraData` | — | Optional metadata fields. Core 0.50.1 does not forward their configured values in global-route requests. |

Upstream keys and secret extra data are encrypted at rest in the `platform` bucket and are not returned by the Configuration API.

:::warning
For global routes using `API_KEY` or a custom header other than `Authorization`, the caller's incoming `Authorization` header can also be forwarded to the upstream by default. `BEARER` and a custom `Authorization` header replace it with the configured upstream key. Review the upstream's trust boundary and [Core header filtering](./2.settings/1.server-and-client.md#proxying).
:::

## Example

```json
{
  "routes": {
    "vector_store_query": {
      "paths": ["/v1/vector_store(/[^/]+)*$"],
      "rewritePath": true,
      "methods": ["GET", "HEAD"],
      "userRoles": ["analyst"],
      "upstreams": [
        { "endpoint": "http://vector-store-1:9876" },
        { "endpoint": "http://vector-store-2:9876" }
      ],
      "maxRetryAttempts": 2
    },
    "rate": {
      "paths": ["/v1/rate"],
      "methods": ["GET", "HEAD"],
      "response": { "status": 200, "body": "OK" }
    },
    "openai-realtime": {
      "paths": ["/openai/realtime"],
      "rewritePath": true,
      "upstreams": [
        {
          "endpoint": "wss://${AZURE_FOUNDRY_PROJECT_NAME}.cognitiveservices.azure.com/openai/realtime",
          "key": "${AZURE_FOUNDRY_API_KEY}"
        }
      ]
    },
    "openrouter": {
      "paths": ["/v1/chat/completions"],
      "rewritePath": false,
      "methods": ["POST"],
      "upstreams": [
        {
          "endpoint": "https://openrouter.ai/api/v1/chat/completions",
          "key": "${OPENROUTER_API_KEY}",
          "authType": "BEARER"
        }
      ]
    }
  }
}
```

## Call an application route

Core exposes an application's routes at:

```text
<METHOD> /v1/deployments/<application>/route/<route_path>
```

- `<METHOD>` is one of the route's `methods`. An empty list accepts any supported method.
- `<application>` is the application's deployment ID.
- `<route_path>` is matched against the route's `paths`. It must not contain the word `route`, so Core can split the deployment ID from the route path.
