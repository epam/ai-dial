# AI Gateway

**AI Gateway** is the section of DIAL Admin where administrators manage models, toolsets, translators,
routes, applications, app runners, and catalog schemas served by DIAL Core.

DIAL Core supports several AI APIs and can distribute model traffic across configured upstreams.
Supported interfaces depend on the deployment. See the [AI API overview](../../2.understand-dial/4.architecture/7.ai-api-overview.md)
and [Load balancing and upstreams](../../7.services/1.core/1.configuration/5.load-balancing.md).

DIAL Core routes requests and applies configured access rules and usage limits. Interceptors run only
on supported API paths; for example, Anthropic Messages passthrough does not run them. Log and trace
export depends on configuration. When enabled, [DIAL Analytics](../5.analytics/0.index.md) provides
usage and cost reports. Connected model providers, applications, and tools can be outside your
environment. For the wider gateway and data flows, see
[Architecture highlights](../../2.understand-dial/4.architecture/1.architecture-highlights.md) and
[Data protection and isolation](../../2.understand-dial/5.security-and-governance/6.data-protection-and-isolation.md).

## What you can manage

Select an item under **AI Gateway** in the DIAL Admin sidebar to open its listing and configuration.

| Item | What you can manage |
|------|---------------------|
| [models](./1.models.md) | Model deployments and their endpoints, features, access, and interceptors. |
| [toolsets](./3.toolsets.md) | Connections to MCP servers that expose tools to DIAL. |
| [translators](./5.translators.md) | Services that convert between supported AI APIs for a deployment. |
| [routes](./4.routes.md) | Paths that proxy requests to upstream endpoints or return configured responses. |
| [applications](./2.applications.md) | Applications and agents that DIAL Core makes available to clients. |
| [app runners](./6.application-runners.md) | Application types and schemas used to create configured application instances. |
| [catalog schemas](./7.catalog-schemas.md) | Metadata fields that models, applications, toolsets, and interceptors can use. |

Manage [roles](../6.governance/1.roles.md), [API keys](../6.governance/2.keys.md), and
[interceptors](../6.governance/4.interceptors.md) in **Governance**. See
[Usage limits and cost control](../6.governance/7.usage-limits-and-cost-control.md) for limits.

## Where an entity can be defined

AI Gateway groups entities by where they are defined. The folders available depend on the entity type
and your access.

| Folder | Source | How it is managed |
|--------|--------|-------------------|
| **file** | DIAL Core configuration files listed in `config.files`. | Read-only in DIAL Admin. To change a file-defined entity, update the configuration file. |
| **platform** | The `platform` bucket in DIAL Core blob storage. | Authorized administrators can create, edit, and delete entities through DIAL Admin or the Configuration API. |
| **public** | The `public` bucket in DIAL resource storage, for applications and toolsets. | Users can publish resources here, and authorized users can create or manage them directly. |

Users can also keep applications and toolsets in private storage and share them with others. Private
resources are not listed in the AI Gateway folders.

## How DIAL Core combines them

DIAL Core merges configuration files and `platform` entities into its runtime configuration. It
resolves `public` applications and toolsets separately when a request uses them.

- **File changes:** Core rereads the files at the `config.reload` interval, which defaults to
  60 seconds. A successful reload updates the runtime configuration without a restart.
- **Platform changes:** A Configuration API write applies on the Core instance that handled it before
  the response. Other instances receive the change through resource events or their next rebuild.
- **Matching definitions:** For supported entity types, a `platform` entity replaces a file-defined
  entity with the same key. Matching rules differ for some types, including routes and keys.
- **Invalid definitions:** The outcome depends on the source and validation settings. Core can retain
  the previous configuration or skip an invalid entity.

For the matching rules, reload behavior, and validation modes, see
[How DIAL Core is configured](../../7.services/1.core/1.configuration/0.index.md#how-the-two-sources-are-merged).

## What happens when you…

| Action | Result |
|--------|--------|
| **Edit a configuration file** | After a successful reload, Core uses the updated definition. It is shown read-only in **file** when that folder is available. |
| **Create or edit a platform entity** | DIAL Admin or the Configuration API writes it to the `platform` bucket. The configuration file is not changed. |
| **Create an application or toolset in public** | DIAL Admin writes it to the selected `public` folder, subject to access permissions. |
| **Publish an application or toolset** | An approved publication places a copy in the target `public` folder. See [Approvals](../6.governance/5.publications-and-review.md). |
| **Copy file-defined entities to platform** | An administrator can use the Core configuration migration endpoint, including a dry run. The copy is not automatic. See [Move file configuration to the platform bucket](../../7.services/1.core/1.configuration/1.configuration-api.md#move-file-configuration-to-the-platform-bucket). |

:::note
To back up Core's `platform` and `public` resources, use the
[Configuration API export](../../7.services/1.core/1.configuration/1.configuration-api.md#export-the-configuration)
or back up the storage. The API export does not include configuration files or encryption key material.
See [Backup and restore](../../5.operating-dial/7.production-readiness/4.backup-and-restore.md).
:::

## Access to entities

Administrators manage `platform` configuration according to DIAL Core's administrator rules. Those
rules can match identity claims or API-key roles. When sign-in is enabled, DIAL Admin forwards the
signed-in user's token to Core.

Role restrictions can control who invokes a platform entity. An unset role list imposes no role
restriction; an explicitly empty list permits no roles. Other access checks still apply.

Access to public applications and toolsets also depends on their folder permissions. In an
organizational unit, unit roles determine access and authorized unit approvers can review publication
requests. For details, see [User management](../6.governance/6.user-management.md) and
[Approvals](../6.governance/5.publications-and-review.md).
