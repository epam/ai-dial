# Deployments overview

Use **Deployments** in DIAL Admin to build container images, run services and Hugging Face models in Kubernetes, and register them for use in DIAL. This section is for administrators managing workloads in an environment configured by their platform team. It does not install DIAL Core, DIAL Chat, or the rest of the platform.

## What you can deploy

DIAL Admin separates **Containers**, for services packaged as container images, from **Model Servings**, for Hugging Face models. An image describes the source to build or copy; a container or model serving is the running workload. A DIAL model, application, interceptor, or Toolset is the configuration that connects DIAL to that workload.

| Workload | Purpose | How you use it in DIAL |
|----------|---------|-----------------------|
| [MCP container](./1.container-management.md#mcp-containers) | Runs an MCP server that exposes tools, resources, or prompts. | Create a [Toolset](../1.ai-gateway/3.toolsets.md) so applications and users can access the server through DIAL. Select a public or available platform destination. |
| [Adapter container](./1.container-management.md#adapter-containers) | Runs a service that translates requests and responses between DIAL and a model-provider API. | Create a [model](../1.ai-gateway/1.models.md) backed by the adapter, then configure its provider connection. The provider's model does not run locally merely because the adapter does. |
| [Application container](./1.container-management.md#application-containers) | Runs custom application logic, which can call models, tools, or other services. | Create an [application](../1.ai-gateway/2.applications.md) in a public or available platform destination and configure its access. |
| [Interceptor container](./1.container-management.md#interceptor-containers) | Runs middleware that processes requests or responses, for example to apply guardrails or filter sensitive data. | Create an [interceptor](../6.governance/4.interceptors.md), then assign it to the models, applications, or other supported configurations where it should apply. |
| [Model serving](./2.model-servings.md) | Runs a Hugging Face model in the cluster. | Create a model for text generation or a Toolset for text classification. The detected task determines the create action; an unsupported capability has no create action. |

For containers, you can use an external Docker image directly or create a versioned [deployment image](./3.images.md) from a Docker image, a Git repository, or an MCP Registry entry. Registry options depend on the server's available packages and transport. See [MCP container creation](./1.container-management.md#create-an-mcp-container) and [adding an image from MCP Registry](./3.images.md#add-an-image-from-mcp-registry).

Model Servings uses a Hugging Face model name instead of a deployment image. See [Create a model serving](./2.model-servings.md#create-a-model-serving-container).

### Adapters and DIAL Model Provider

An [adapter](../../4.building-with-dial/4.adapters/0.index.md) connects DIAL to a provider's API; a model serving runs the model itself. [DIAL Model Provider](../../7.services/4.model-provider/0.index.md) packages the OpenAI, Vertex AI, Bedrock, and DIAL-to-DIAL adapters in one service. It is not another container type in DIAL Admin.

Each bundled adapter has a `/compat/<adapter>` path. When replacing standalone adapters with DIAL Model Provider, update model endpoints to use the corresponding path. See [Migrate from the standalone adapters](../../7.services/4.model-provider/2.migration.md).

:::note
The optional legacy Admin API also exposes adapter configurations and other entity-creation actions. The workflow below describes creating models, applications, interceptors, and toolsets in the current DIAL configuration. See [Where an entity can be defined](../1.ai-gateway/0.index.md#where-an-entity-can-be-defined) for the configuration sources.
:::

## Where workloads run

DIAL Admin sends build and deployment requests to **DIAL Deployment Manager Backend**. The backend connects to Kubernetes and creates resources in the namespaces configured by the platform team. A namespace groups Kubernetes resources; build jobs and workloads can use different namespaces. Workloads do not run inside the Admin frontend or DIAL Core process.

| Operation | Where it runs | Infrastructure used |
|-----------|---------------|---------------------|
| Build, analyze, or copy an image | The configured build namespace. | Kubernetes jobs. BuildKit builds container images from source. |
| Run an MCP server, adapter, application, or interceptor | The configured container namespace. | Knative, which runs service containers and supports request-driven scaling. |
| Run a Hugging Face model | The configured model-serving namespace. | KServe, which manages model inference workloads. |

The platform team configures the Kubernetes connection, target namespaces, and permissions in [Deployment Manager Backend configuration](../../7.services/11.deployment-manager/1.configuration/1.backend.md#kubernetes-connection-and-rbac). Deployment Manager stores image and workload definitions in its own database. Use H2 for development or testing, and PostgreSQL or SQL Server for production.

Management and runtime requests take different paths:

```text
Management: DIAL Admin -> Deployment Manager -> Kubernetes jobs and services
Runtime:    Client -> DIAL Core -> registered workload endpoint
```

Creating a workload and registering it in DIAL are separate operations. Registration tells DIAL how to reach the workload; it does not move the workload into DIAL Core. A service URL can be cluster-internal, so it is not necessarily reachable from a user's workstation.

:::warning
Deploying an adapter or application in your cluster does not guarantee that all processing stays there. The service can call an external model provider, MCP server, or enterprise system. See [Deployment profiles](../../2.understand-dial/4.architecture/3.deployment-profiles.md#place-the-boundaries) for network, data-processing, and operating boundaries.
:::

## Prerequisites

Your platform team must prepare the environment before you deploy workloads:

- **DIAL Admin and Deployment Manager**

  Enable Deployments and configure the backend API URL. Model Servings also requires the frontend's Hugging Face option. See [DIAL Admin deployment settings](../../7.services/9.admin/2.configuration/1.frontend.md#deployment-manager-and-mcp-containers).
- **Kubernetes runtimes**

  Install and configure Knative for ordinary containers. For Hugging Face models, also install KServe and enable its integration in Deployment Manager; it is disabled by default. See [Workload deployment](../../7.services/11.deployment-manager/1.configuration/1.backend.md#workload-deployment).
- **Compute capacity**

  Provide nodes with sufficient CPU and memory, and GPUs when the model requires them. Configuring resources in DIAL Admin assigns existing capacity; it does not provision cluster nodes.
- **Image and source access**

  Configure registry access for image builds and credentials for private Git repositories. Allow the required domains when firewall policies are enforced. See [Image builds and registries](../../7.services/11.deployment-manager/1.configuration/1.backend.md#image-builds-and-registries) and [Private Git repositories](../../7.services/11.deployment-manager/1.configuration/1.backend.md#private-git-repositories).

[DIAL Core](../../7.services/1.core/0.index.md) must be configured to make registered models, applications, and Toolsets available through DIAL. Administrators also need permission to deploy workloads and manage the resulting configurations.

## Typical workflow

1. **Choose the workload and source**

   For a service container, select a Docker image or add and install a [deployment image](./3.images.md). For a Hugging Face model, use [Model Servings](./2.model-servings.md) instead.
2. **Create the workload**

   Enter its identifier, display name, and source settings. Creation opens its configuration screen; it does not start the workload.
3. **Configure and save**

   Review the endpoint, compute, scaling, environment variables, startup probe, and firewall settings that apply to the workload. A startup probe checks whether the service is ready to handle traffic. Save any changes before running it.
4. **Run and check readiness**

   Click **Run** and wait for **Running**. Use the execution log, Kubernetes events, and metrics to investigate failures.
5. **Register it in DIAL**

   Use the available create action to create the model, application, interceptor, or Toolset. DIAL Admin pre-populates the source or endpoint. Configure access, and assign an interceptor where it should apply.

For detailed steps, use [Manage containers](./1.container-management.md), [Model Servings](./2.model-servings.md), or [Manage deployment images](./3.images.md). [AI Gateway](../1.ai-gateway/0.index.md) explains how the resulting models, applications, and Toolsets are configured and made available.

## Operate and secure workloads

- **Scale and stop**

  Configure replica limits and, where supported, automatic scale to zero to reduce idle compute use. Stop workloads you no longer need. Model-serving scaling defaults differ from ordinary containers; see [shared properties](./1.container-management.md#properties) and [model-serving properties](./2.model-servings.md#model-serving-properties).
- **Select compute**

  Set CPU and memory requests and limits. GPU requests are available for model servings. If the platform team configures node pools, choose one in **Compute** to schedule the workload on suitable nodes, for example GPU nodes. See [Node pool selection](./1.container-management.md#node-pool-selection).
- **Control outbound access**

  Choose all domains or specific allowed domains for a workload or image build. The global list applies to image builds only; containers have separate rules. Enforcement requires Cilium, the cluster network-policy integration, to be configured. See [container firewall settings](./1.container-management.md#firewall-settings), [image firewall settings](./3.images.md#firewall-settings), and [Network policy](../../7.services/11.deployment-manager/1.configuration/1.backend.md#network-policy).
- **Manage credentials**

  Use sensitive environment-variable values for service credentials. Deployment Manager stores them as Kubernetes Secrets. See [container properties](./1.container-management.md#properties).
- **Troubleshoot and maintain**

  Inspect build logs, execution logs, events, and metrics. Publish new image versions and update container settings as needed. The **Audit** tab is available only when the legacy Admin API is enabled; it is not a prerequisite for deployment.

## Components and repositories

| Component | Role | Repository |
|-----------|------|------------|
| DIAL Admin | Provides the Images, Containers, and Model Servings management screens. | [ai-dial-admin-frontend](https://github.com/epam/ai-dial-admin-frontend) |
| [DIAL Deployment Manager Backend](../../7.services/11.deployment-manager/0.index.md) | Builds images, manages Kubernetes workloads, and reports their status, logs, events, and metrics. | [ai-dial-admin-deployment-manager-backend](https://github.com/epam/ai-dial-admin-deployment-manager-backend) |
| DIAL Core | Routes requests to registered models, applications, and Toolsets, and applies configured interceptors and access controls. | [ai-dial-core](https://github.com/epam/ai-dial-core) |
| [MCP proxy images](../../7.services/11.deployment-manager/1.configuration/2.mcp-proxy.md) | Supply the executable added during image builds to expose MCP servers that use standard input/output (stdio) over Streamable HTTP. They are not a separate proxy deployment. | [ai-dial-deployment-manager-mcp-proxy](https://github.com/epam/ai-dial-deployment-manager-mcp-proxy) |
| DIAL Model Provider | Optional runtime service that hosts the official model adapters together. | [ai-dial-model-provider](https://github.com/epam/ai-dial-model-provider) |

For custom development, use the [DIAL SDK](../../4.building-with-dial/5.developer-tools/1.sdk-reference/0.index.md) to implement adapters and applications. It is a development library, not another service required by Deployments.
