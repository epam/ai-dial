# Deployments overview

The Deployments section of DIAL Admin lets you run and manage workloads in your Kubernetes cluster. You can deploy MCP servers, model adapters, applications, interceptors, and Hugging Face models, then register their endpoints for use in DIAL.

## What you can do

* **Bring your own MCP servers.** Deploy an MCP server from the [MCP Registry](https://registry.modelcontextprotocol.io/),
  a Docker image or a Git repository, and expose its tools to DIAL users as a
  [toolset](../1.ai-gateway/3.toolsets.md).
* **Self-host models.** Run a Hugging Face model as a [model serving](./2.model-servings.md). Depending on the task, create a DIAL model or Toolset from the running serving.
* **Connect model providers.** An [adapter](../../4.building-with-dial/4.adapters/0.index.md) translates requests between DIAL and a model provider. Deploy an adapter container, then configure a model to use it. [DIAL Model Provider](../../7.services/4.model-provider/0.index.md) bundles the OpenAI, Vertex AI, Bedrock, and DIAL-to-DIAL adapters in one service.
* **Run applications and interceptors.** Deploy them from an image or source code, then register an [application](../1.ai-gateway/2.applications.md) or [interceptor](../6.governance/4.interceptors.md).
* **Build from source.** Build images from a Git repository (a branch and a commit), including private
  repositories, or use a ready-made Docker image from an external registry.
* **Operate your workloads.** Start and stop containers, scale them (including scale to zero), set CPU,
  memory and GPU resources, pin them to node pools, manage environment variables and startup probes.
* **Troubleshoot.** Read build and execution logs, Kubernetes events and resource metrics, and review the
  audit log of changes.
* **Control network access.** Allow a container or an image build to reach only the domains you list,
  with a global list plus per-image and per-container rules.

## How it works

```text
Source                        DIAL Admin                     DIAL
──────                        ──────────                     ────
Docker image        ┐
Git repository      ├─► Image ──► Container ──────► Endpoint ──► Configuration
MCP Registry        ┘   (build)   (run, scale)
Hugging Face model ────────────► Model serving ───► Endpoint ──► Configuration
```

1. An **image** describes what to run: a Docker image, source code to build, or an MCP server from the
   MCP Registry. Images of source code are built in your cluster.
2. A **container** runs an image (or an external Docker image directly) as a serverless workload that scales on
   demand and gets an HTTPS endpoint. A **model serving** container runs a Hugging Face model.
3. From a running workload, create the corresponding DIAL configuration. The available action depends on the workload and, for a model serving, its detected task. DIAL then calls the workload's endpoint when the registered model, application, or Toolset is used.

### Workloads and DIAL configurations

| Workload | Purpose | What you can create |
|----------|---------|---------------------|
| [MCP container](./1.container-management.md#mcp-containers) | Runs an MCP server. | A Toolset in the public or platform folder. |
| [Adapter container](./1.container-management.md#adapter-containers) | Runs an adapter that connects a model provider to DIAL. | A model, or an adapter configuration when the Admin API is enabled. |
| [Application container](./1.container-management.md#application-containers) | Runs an application that implements its own logic. | An application. |
| [Interceptor container](./1.container-management.md#interceptor-containers) | Runs middleware that processes requests or responses. | An interceptor. |
| [Model serving](./2.model-servings.md) | Runs a Hugging Face model. | A model for text generation or a Toolset for text classification. Some detected capabilities have no create action. |

Behind the screens, the **Deployment Manager Backend** does the work in Kubernetes: it builds images
with BuildKit jobs, runs workloads as Knative services (and Hugging Face models with KServe), streams
status, logs and events to Admin, and keeps its state in a database (H2 for development; PostgreSQL or SQL Server
for production).

The Deployments menu appears in DIAL Admin when deployments are enabled and the Deployments API URL is
configured; model servings also need Hugging Face support enabled. See
[DIAL Admin deployment settings](../../7.services/9.admin/2.configuration/1.frontend.md#deployment-manager-and-mcp-containers).
To deploy and configure the backend and its stdio MCP proxy images, see
[DIAL Deployment Manager](../../7.services/11.deployment-manager/0.index.md).

## Concepts

| Concept | Description |
|---------|-------------|
| **Image** | The build source of a workload: an MCP server, adapter, application or interceptor. Its source is a Docker image, a source code repository (URL, branch and commit SHA) or the MCP Registry. Images are versioned. See [Images](./3.images.md). |
| **Container** | A running instance of an image, or of an external Docker image. Types are MCP, adapter, application and interceptor. It has resources, scaling, environment variables, a startup probe and firewall rules. See [Containers](./1.container-management.md). |
| **Model serving** | A container that runs a Hugging Face model in your cluster. See [Model servings](./2.model-servings.md). |
| **DIAL configuration** | A model, application, interceptor, or Toolset that connects DIAL to a workload. DIAL Admin can also manage adapter configurations used by models. |
| **Firewall** | The list of domains a container or an image build may connect to. A global list applies to all image builds. |
| **Node pool** | A group of cluster nodes, for example GPU nodes. You pin a container to a pool in its Compute settings. |

## Typical workflow

For MCP servers, adapters, applications, and interceptors:

1. **Add an image** from a Docker image, a Git repository or the MCP Registry, and wait until it is
   installed. See [Images](./3.images.md). You can skip this step for an external Docker image.
2. **Create a container** from the image (or from an external Docker image reference). See
   [Containers](./1.container-management.md).
3. **Configure and run it**: set the endpoint, resources, scaling, environment variables, startup probe
   and firewall, then run it. Check the status, the execution log and the metrics.
4. **Create a DIAL configuration** from the running container. Depending on the workload, create a Toolset, model, application, or interceptor; an adapter container can also create an adapter configuration when the Admin API is enabled.
5. **Maintain it**: update the configuration, publish a new image version, stop containers that are not
   needed, and review the audit log.

For a Hugging Face model, use [Model Servings](./2.model-servings.md) instead: create and configure the serving, run it, and create a model or Toolset according to its detected task.

## Common scenarios

| Goal | Approach |
|------|----------|
| Make an MCP server available to users | Add an image of type MCP from the MCP Registry, deploy it as an MCP container, and create a toolset from it. See [MCP containers](./1.container-management.md#mcp-containers). |
| Self-host an open model | Create and run a Hugging Face model serving, then create a model or Toolset according to its task. Use a GPU node pool for large models. See [Model servings](./2.model-servings.md). |
| Deploy your own application or adapter | Build an image from your repository, deploy it as an application or adapter container, and create the entity. |
| Add an interceptor | Deploy an interceptor image as a container, and create an interceptor from it. |
| Build from a private repository | Add the image from source code, and allow the repository's domain in the image firewall. |
| Save cost on rarely used workloads | Keep automatic scale to zero on, so a container uses no replicas when idle. |
| Lock down a workload | Restrict its outgoing traffic with firewall rules. Sensitive environment variables are stored as Kubernetes Secrets. |
