# Evaluation overview

The Evaluation section of DIAL Admin lets you measure how well a model, an application, a DIAL Core route
or an MCP tool works, and check that it keeps working after you change it. You describe what to test in a
dataset, choose how to score the answers with metrics, run the test suite against a deployment, and read or
compare the results — all in DIAL Admin.

A **test suite** ties one target (the model, application, route or MCP tool to evaluate) to test cases and
metrics. Each **run** of a test suite sends the test cases to the target and scores the answers.

## What you can do

* **Benchmark** a model, an application or a route on your own test cases: accuracy, answer relevance,
  faithfulness to retrieved context, or any custom criteria.
* **Evaluate RAG applications**: score retrieval and answer quality with ready-made metrics.
* **Test MCP tools**: call a tool of an MCP toolset with test arguments and check the result.
* **Test multi-step behavior**: multi-turn dialogues, and chains of several requests per test case
  where each request uses the results of the previous ones. Chains are not available for MCP tools.
* **Catch regressions**: re-run the same test suite after a change, compare two runs side by side,
  and follow score trends across runs. A score threshold marks which test cases and runs pass.
* **Analyze and share results**: drill down to a single test case, see cost and timing, open traces in Grafana,
  and export results to CSV.
* **Automate**: run test suites from a pipeline with `eval-cli`, which executes them against a target
  deployment and imports the results back into the Runs list.

## Concepts

| Concept | Description |
|---------|-------------|
| **Dataset** | A reusable collection of test cases with a defined schema. Datasets are independent of test suites and can be shared across many of them. Test cases you add directly in a test suite stay private to it until you use **Publish to a new dataset**. See [Datasets](3.datasets.md). |
| **Test case** | One row of test data in a dataset: the input for the target and, optionally, the expected output. Fields can be string, number, integer, boolean, object, array, file or skill (a DIAL skill picked from the catalog; not available for response columns). A test case can be multi-turn. |
| **Metric** | A scoring function that evaluates a response, for example Faithfulness, Answer Relevancy or Exact Match. A metric is attached to a test suite, where its inputs are bound to test case fields, response fields or constants. |
| **Test suite** | Ties together a target (a model, an application, a DIAL Core route or an MCP tool), a dataset, a request template and metrics. A request can go to any endpoint the target declares, including the OpenAI Chat Completions, OpenAI Responses and Anthropic Messages APIs. See [Test suites](1.test-suites.md). |
| **Run** | One execution of a test suite. It records per-test-case scores, an overall score, status, timing, cost and traces. Runs can be stopped, compared and exported. See [Runs](2.runs.md). |

## Choose what to evaluate

A test suite evaluates one target. What you select, what the test suite sends, and which features apply
depend on the kind of target. Metrics, score thresholds, runs and comparison work the same way for all of them.

| Target | What you select | What the test suite sends | Specifics |
|--------|-----------------|---------------------------|-----------|
| **Model** | A model, then an endpoint that it declares, for example Chat Completions. | A request built from the request template, with variables filled from each test case. | Request chains and multi-turn test cases are supported. The run cost includes the target and the metrics. |
| **Application** | An application, then an endpoint that it declares. | The same as for a model. | The same as for a model. |
| **DIAL Core route** | A route, then an endpoint of the route. | The same as for a model. | The same as for a model, except that the run cost includes only the metrics. |
| **MCP tool** | An MCP toolset, then one of its tools. | A call of the tool with the argument values that you enter. A `${{field}}` placeholder takes the value from the test case. | There is no request template, request chain or multi-turn test case. The result of the call is read into extracted response fields. The run cost includes only the metrics. |

For the configuration of each kind, see [Method](1.test-suites.md#method) and
[MCP tool suites](1.test-suites.md#mcp-tool-suites) in Test suites.

## Example: evaluate a model

This example checks a model on three questions with known answers. It uses a rule-based metric, so it
needs no judge model.

1. **Create the test suite.** Open **Evaluation > Test Suites** and click **Create**. Enter a name, select
   the model on the **Models** tab and select its **Chat Completions** endpoint. The new test suite starts
   with an empty private dataset for its own test cases.
2. **Add test cases.** On the **Test Cases** tab, click **Configure schema** and add two fields,
   `user_message` and `expected_answer`. Click **Add** three times and fill in the fields, for example
   "What is the capital of France? Answer with one word." and "Paris".
3. **Check the request.** On the **Method** tab, click **Edit request** and go to **Configuration**. The
   default body sends the variable `${{user_message}}` as the user message, and a `temperature` of 0.7.
   If your model rejects `temperature`, delete that line from the body and click **Save**.
4. **Bind the variable.** In **Dynamic configuration**, set `user_message` to **Test Case Columns** and
   select the column `user_message`. Click **Try out** and **Send Request** to check that the model answers.
5. **Check the extracted answer.** **Extracted response fields** already contains `answer`, which reads
   `choices[0].message.content` from the response.
6. **Add the metric.** On the **Metrics** tab, click **Add** and select **Exact Match**. Bind `actual` to
   the response column `answer` and `ground_truth` to the test case column `expected_answer`.
7. **Run.** Click **Run** in the header and confirm.
8. **Read the result.** Open the run from the **Runs** tab. The **Summary** tab shows the **Overall
   Score**, and the **Extraction result** tab shows each answer next to its score. See
   [Reading run results](2.runs.md#reading-run-results).

:::note
Some models don't accept `temperature`. They reject the request with an error such as "`temperature` is
deprecated for this model".
:::

For an application, select it on the **Applications** tab of the **Target** step instead. The endpoints you can
choose are the ones that the application declares. For an MCP tool, see the
[next example](#example-evaluate-an-mcp-tool).
To share the test cases with other test suites,
[publish them to a new dataset](1.test-suites.md#publish-to-a-dataset) or create a
[dataset](3.datasets.md) first and attach it.

## Example: evaluate an MCP tool

This example calls one read-only tool of an MCP toolset with two test arguments and checks that the result
contains an expected text.

:::note
If the toolset requires authentication, log in to it first on its page in DIAL Admin. While the toolset is
logged out, access to its list of tools is revoked, so you can't select a tool.
:::

1. **Create the test suite.** Open **Evaluation > Test Suites** and click **Create**. Enter a name, select
   the toolset on the **MCP** tab, and select a tool on the **Tool** step. Choose a tool that only reads,
   for example a search tool.
2. **Add test cases.** On the **Test Cases** tab, click **Configure schema** and add a field with the same
   name as the tool argument that you will vary, for example `query`. Click **Add** twice and enter a
   different value in each test case.
3. **Set the argument.** On the **Method** tab, in **Tool Arguments**, enter `${{query:default}}` as the
   **Value** of that argument. The test case value is used when it exists, and `default` otherwise. Without
   a default, the test suite stays invalid. Click **Try out** and **Send Request** to see the result of the
   tool.
4. **Extract the value to check.** On the **Columns** tab, click **Add** and define a field that reads the
   text of the result, with a JSONata **JSON Path**. The **Output Schema** tab shows the structure of the
   result.
5. **Add the metric.** On the **Metrics** tab, click **Add** and select **Regex Match**. Set `pattern` to a
   regular expression that every correct result matches, and bind `actual` to your extracted field.
6. **Run and read the result.** Click **Run**, open the run from the **Runs** tab, and check the score and
   the extracted field in **Extraction result**.

For the MCP-specific settings, see [MCP tool suites](1.test-suites.md#mcp-tool-suites).

## Typical workflow

1. **Prepare test cases**, in a [dataset](3.datasets.md) or manually in the test suite.
2. **Set up the test suite**: target, request, metrics and score threshold. See
   [Set up a test suite](1.test-suites.md#set-up-a-test-suite).
3. **Run** the test suite. Use **Try out** on one test case first to check the request.
4. **Read the results** on the run Summary and Extraction result tabs. See
   [Reading run results](2.runs.md#reading-run-results).
5. **Improve and repeat**: change the application, prompt or model, run again, then
   [compare runs](2.runs.md#compare-runs) and watch the [trends](1.test-suites.md#trends).

## Common patterns

| Goal | Approach |
|------|----------|
| Check an application after a change | Keep one test suite, run it before and after the change, and compare the two runs. A drop in the heat map or in the metric statistics shows the regression. |
| Evaluate a RAG application | Extract the answer and the retrieved context from the response into response columns, add retrieval and faithfulness metrics, and bind their inputs to those columns and to the expected answer in the dataset. |
| Judge answers by your own criteria | Add the G-Eval metric with a description of the criteria or a list of evaluation steps. |
| Check exact or structured output | Use rule-based metrics such as Exact Match, Regex Match or DeepDiff. They need no judge model. |
| Test an agent's tool calls | Use the Tool Call Accuracy and Tool Call F1 metrics to compare the tool calls the agent makes with the expected ones. |
| Test a multi-turn dialogue | Use per-turn schema fields in the dataset, and a metric **Condition** such as `turn.last` to score only the final answer. |
| Gate a release | Set a score threshold in the test suite, and look at **Threshold Pass Rate of Latest Run** on the Trends tab. Run the suites from a pipeline with `eval-cli`. |

## How it works

```text
DIAL Admin (Evaluation screens)
        │  Evaluation API
        ▼
Evaluation framework backend ──► DIAL Core ──► evaluated model, application or MCP tool
        │                            ▲
        │ metric requests            │ judge model calls
        ▼                            │
Evaluation metrics service ──────────┘

Results are stored in PostgreSQL (suites, datasets, runs and analytics).
```

1. You work in **DIAL Admin**. It sends requests to the evaluation framework backend.
2. For each test case, the **evaluation framework backend** sends the request from the test suite to the
   target deployment through **DIAL Core**, and extracts the response fields you defined.
3. It then asks the **evaluation metrics service** to calculate the metrics. Metrics that use a language
   model as a judge call a model deployed in DIAL Core.
4. Scores, timing and cost are stored, and DIAL Admin shows them in runs.

The Evaluation menu appears in DIAL Admin when the Evaluation API URL is configured. See
[DIAL Admin evaluation settings](../../6.services/9.admin/2.configuration/1.frontend.md#evaluation).
To deploy and configure the evaluation services, see [DIAL Evaluations](../../6.services/10.evaluations/0.index.md).
