Manage AI models

DIAL Core can serve any model you can reach over HTTP. You register the model in DIAL Admin with a working endpoint, and clients then call it by name through DIAL Core. They get the same access control, rate limits, interceptors, load balancing and logging as for every other model.

A model can be reached in three ways:

  • External deployment. Point DIAL Core at the endpoint of a model hosted by a cloud vendor or another provider.
  • Internal model serving. Point it at a model served by a container that you run in DIAL.
  • Adapter. Point it at an adapter, a service that sits between DIAL Core and a model whose API is not directly compatible.

Models can speak different APIs. DIAL Core supports OpenAI Chat Completions, OpenAI Responses, Anthropic Messages and OpenAI Embeddings interfaces. A model that speaks one of them is used directly, without an adapter. For a model that speaks a different API, use an adapter or a translator, which converts requests from one LLM API to another. A model can also declare several interfaces and serve different protocols from one deployment.

You can add models in DIAL Admin or by editing the DIAL Core configuration. This page describes DIAL Admin. You need administrator permissions. See Supported Models for the providers DIAL supports.

Main screen​

On this page, you can find all AI model deployments available on your DIAL instance. Here you can view, filter, and add new model definitions.

When a model deployment is successfully added in DIAL Admin AI Gateway section, it is stored in a dedicated blob storage and can be accessed across the DIAL ecosystem including DIAL Chat and via the API for authorized user roles.

Columns differ by bucket. Every column (except in the file bucket) has an inline search/filter box.

File bucket: a single Name column (the config-entity name). No other columns, and no actions.

Folders​

The left panel shows where each model definition is stored. It has two root folders:

  • file: models defined in the DIAL Core configuration file. This folder is read-only; it lists only the model names. To change these models, edit the DIAL Core config file.
  • platform: models stored in DIAL Core platform blob storage. This is where you create, edit and delete models in DIAL Admin.

Select a folder to list its models in the grid. See AI Gateway for how DIAL Core combines the two sources.

Create model​

Follow these steps to add a new AI model definition to your DIAL instance:

  1. Click Create to invoke a Create Model modal.

  2. Define parameters for a new model:

    FieldRequiredDescription
    IDYesUnique identifier used by the model adapter to invoke the model's backend.
    Display NameYesModel name shown across the UI (e.g. "GPT-4 Turbo").
    Display versionNoOptional tag to track releases when you register multiple variants of the same model (e.g. 2024-07-18, v1).
    DescriptionNoFree-text note about the model's purpose or distinguishing traits.

  3. Click Create to close the dialog and open the configuration screen. When done with model configuration, click Save. It may take some time for the changes to take effect after saving. Once added, the model appears in the Models listing and becomes available to use across the DIAL ecosystem.

Configuration​

You can access the model deployment configuration screen by clicking any model deployment on the main screen, or when adding a new model deployment. In this section, you can view and configure all settings for the selected model deployment.

  • Properties: Main definitions and runtime settings.
  • Features: Optional capabilities and custom endpoints.
  • Catalog metadata: Values for the fields of the catalog schema attached to the model.
  • Roles: Roles that can invoke this model.
  • Interceptors: Custom logic to modify requests or responses.
  • Audit: Usage dashboard and request traces for the model.

Properties​

In the Properties tab, you can view and edit main definitions and runtime settings for a model deployment.

  • Basic information: Identification and basic information about the model and its author.
  • Endpoints: Model's endpoints.
  • Interfaces: The LLM APIs the model serves (OpenAI Chat Completions, OpenAI Responses, Anthropic Messages, OpenAI Embeddings) and how requests reach them.
  • Personalization: Parameters to customize the model's appearance on UI.
  • Attachments: Define attachment types and maximum number of attachments the model can accept.
  • Default parameters: Set default values for model parameters used in chat/completions and responses requests.
  • Upstream configuration: Define upstream endpoints, authentication keys, weights, and extra data.
  • Advanced options: Tokenizer model, forward auth token, interaction limits, retry attempts.
  • Cost configuration: Set cost unit, prompt price, and completion price for real-time billing.
  • Catalog schema: The catalog schema that defines this model's catalog metadata.

Interfaces​

DIAL supports OpenAI Chat Completions, OpenAI Responses, Anthropic Messages and OpenAI Embeddings interfaces. To standard endpoints you can add alternatives.

When provided, DIAL Core forwards each request to that base URL followed by the path the request arrived on. An interface listed without a base URL of its own uses the model-level Base URL. If neither is set, requests to that interface fail with HTTP 503.

FieldRequiredDescription
Base URLOptionalThe root URL that the matching ingress path is appended to. The model-level Base URL serves an entry that omits it.
ModeNoPassthrough (default) or translator. It declares whether the request is forwarded in the shape it arrived in, or handed to a service that translates it into an API the model does speak. A translator interface does not touch the caller's role limits — neither checks nor charges them. The translator calls DIAL Core back to have the completion served, and that second call is the real request: it carries the tokens, the cost and the requestHour/requestDay slot, so a client call is counted once rather than twice. An exhausted quota is therefore enforced on the callback rather than on the translated call itself.
TranslatorOptionalThe translator serving this interface, required by mode: translator and rejected without it. An interface is served either by a base URL or by a translator, never by both — a model declaring both is rejected on config load.
Default HeadersNoHeaders applied to requests for this interface only, laid over the model-level Default Headers.
FeaturesNoFeature fields that override model-level features for this interface only. Unspecified fields inherit the model-level value, then Core defaults apply.
DefaultsNoBody parameters applied to requests for this interface only, replacing whichever model-level defaults would otherwise serve it. They are injected the same way the model-level ones are — a key the request already carries is never replaced.
Override PathsNoPer-operation upstream paths that replace the default "base URL + ingress path" routing for this interface.

Refer to DIAL Core documentation to learn more about interfaces, how to configure them and how they work.

Default parameters​

Default parameters can be used to pass additional parameters with the chat completion or responses requests.

FieldRequiredDescription
Completion DefaultsNoDefault parameters are applied if a request doesn't contain them in an OpenAI chat/completions or embeddings API call. They are not applied to Responses API or Anthropic Messages requests.
Responses DefaultsNoDefault parameters are applied if a request doesn't contain them in an OpenAI openai/v1/responses API call. Available if the OpenAI Responses API is supported.
Default HeadersNoHTTP headers DIAL Core adds to a request that doesn't already carry them, for every interface the model serves. Note

Defaults set for a specific interface replace the model-level defaults for that interface instead of being merged with them. Anthropic Messages requests get defaults only from their own interface.

Upstream configuration​

You can use upstream endpoints to provide alternative URLs DIAL Core will use to send chat completions and responses requests. This enables weighted load balancing and tiered fallback among multiple hosts. Refer to Load Balancer to learn more. For example, you can provide a model's Docker container URI if the model's container is deployed in DIAL. Refer to Model Servings to learn more about this use case.

FieldDescription
IDIdentifier of the upstream endpoint. It uniquely identifies this upstream within the model's upstream list, and clients can send it in the X-UPSTREAM-ID request header to pin a request to this upstream. Required when the model has a Responses endpoint (it routes follow-up Responses API requests to the same upstream) and when the upstream declares interfaces. Otherwise optional.
Upstream EndpointsThe upstream backend URL for the chat completions API. Passed to the model adapter in the X-UPSTREAM-ENDPOINT header. It also serves the embeddings and Anthropic Messages APIs unless they are configured explicitly.
Responses endpointThe upstream backend URL for the Responses API. Shown only when the model supports the Responses API. Passed to the model adapter in the X-UPSTREAM-ENDPOINT header when routing Responses API requests.
WeightNumeric weight for this endpoint in a multi-upstream scenario. Higher = more traffic share. Default: 1. A weight of zero or less excludes the endpoint from routing.
TierSpecifies an endpoint group. In a regular scenario, all requests are routed to endpoints with the lowest tier value (the highest priority), but in case of an outage or hitting the limits, the next one in the line helps to handle the load. Default: 0, the highest priority.

Click the expand chevron on an upstream row to reveal additional fields:

FieldDescription
Base URLThe provider root URL for this upstream. DIAL Core completes it with the standard path of each interface that declares no endpoint of its own: /v1/chat/completions, /v1/embeddings, /v1/responses or /v1/messages. An interface endpoint, when set, takes precedence.
KeyAPI key, token, or credential passed to the upstream. Masked — click the eye icon to reveal. DIAL Core never returns a saved key, so the field is empty for an existing upstream. Leave it empty to keep the stored key.
Extra DataFree-form JSON or string metadata passed to the model adapter with each request.
Secret Extra DataSensitive key-value metadata passed to the model adapter alongside Extra Data. Values are masked in the UI and in server logs. Use this for credentials or tokens the adapter needs at runtime.
InterfacesPer-upstream overrides for individual interfaces (OpenAI Chat Completions, OpenAI Responses, Anthropic Messages, OpenAI Embeddings). Click + Add and select a type. Each entry has the fields in the table below.

Each upstream interface entry overrides that interface for this upstream only. Fields that you leave unset fall back to the upstream's own values.

DIAL Core matches a stored key and secret extra data to an upstream by its endpoint. If you change the endpoint of an existing upstream and leave the key empty, DIAL Admin warns that the stored credentials cannot carry over. Enter the key and secret extra data again before saving.

Cost configuration​

Enables real-time cost estimation and quota enforcement. Powers the monitoring dashboards with per-model spending metrics.

FieldRequiredDescription
Cost unitYesBase unit and scale for billing. Select the unit type and scale (e.g. "per million").
Available unit types:
None: Disables all cost tracking for this model.
Tokens: Every token sent or received by the model is counted towards your cost metrics.
Char without whitespace: Tells DIAL to count only non-whitespace characters (letters, numbers, punctuation) in each request as the billing unit.
Prompt priceYesCost per unit for prompt tokens.
Completion priceYesCost per unit for completion tokens (chat responses).
Cache read/write priceNoCost per cache-read/cache-write token. Available only when the Cost unit is Tokens. Each is either a flat rate string (same convention as prompt/completion) or a decision-tree object that picks a rate based on the call's own usage data — the field is either a standard name or a $-prefixed JSON Path expression. Left unset, cache tokens are billed at the prompt rate, exactly as if caching weren't split out at all.

Catalog schema​

A catalog schema is a structured set of fields defined centrally. You create a schema in Catalog schemas and attach it to a model here. Click the selector to pick a schema, or Browse to choose one. Selecting a schema enables the Catalog metadata section.

Features​

In the Features tab, you can enable, disable, or override optional capabilities for a specific model. Use model features to tell DIAL Core what the model supports — turning features on when your model supports them, or off when it doesn't.

Some model adapters expose specialized HTTP endpoints for tokenization, rate estimation, prompt truncation, or live configuration. You can point DIAL Core to them in this section.

Model features apply per AI model, controlling what the model endpoint itself supports (e.g. whether GPT-4 can accept system prompts or function calls).

Tip

Enable only the features you need. Extra toggles can cause errors if the upstream doesn't support them. After setting a custom endpoint, test it via a simple API call to confirm accessibility and authentication.

Custom endpoints​

Some model adapters expose specialized HTTP endpoints for tokenization, rate estimation, prompt truncation, or live configuration. Specify them in this section.

FieldDescription
Rate endpointURL to invoke the model's cost-estimation or billing API. Call an endpoint that returns token counts and credit usage. Override if your adapter supports a dedicated "rate" path.
Tokenize endpointURL to invoke a standalone tokenization service. Use when you need precise token counts before truncation or batching. Models without built-in tokenization require this.
Truncate prompt endpointURL to invoke a prompt-truncation API. Ensures prompts are safely cut to max context length. Useful when working with very long user inputs.
Configuration endpointURL to fetch JSON Schema describing settings of the DIAL model. DIAL Core exposes this endpoint to DIAL clients as GET v1/deployments/<deployment name>/configuration. DIAL client must provide a JSON value corresponding to the configuration JSON Schema in a chat completion request in the custom_fields.configuration field.

Reasoning​

Reasoning Efforts defines the reasoning effort levels the model supports (e.g. low, medium, high). When configured, DIAL Chat displays a selector that lets users choose a reasoning effort for each request. Leave empty if the model does not support reasoning effort control.

Feature flags (toggles)​

Model toggles ensure you don't accidentally send unsupported parameters to a given model.

Each toggle corresponds to a chat completion feature that DIAL Core handles. Enable them only if your model and adapter fully support that feature. Toggles are organized into named groups (Sampling & Output Control, Tools, Functions & Skills, Prompt & Message Composition, Attachments, Caching, Session & Access, Feedback).

By default, DIAL Core treats the following features as enabled: System prompt, Parallel tool calls, Max tokens, Custom temperature, Allow resume and Accessible by request key. The Temperature supported, Seed, Max completion tokens, Tools, Content parts, URL Attachments, Folder Attachments, Assistant attachment in request, Cache and Auto caching toggles are disabled by default, and no Reasoning Efforts are set.

Catalog metadata​

Catalog metadata holds the values for the fields of the catalog schema attached to the model. The section is empty until you select a schema in the Catalog schema field on Properties:

  • No schema selected — the section shows "Select a catalog schema on the Properties tab to edit its catalog metadata."
  • Schema selected — the schema's fields render for you to complete. Use the View selector to switch between a generated Form and raw JSON. A banner flags any stored properties the schema does not declare.

Role-specific access​

Use the Make available to specific roles toggle to define access to the model:

  • Off: Model is callable by any authenticated user. The grid lists all roles and is read-only.
  • On: Model is restricted — only the roles you explicitly add to the grid can invoke it. With no roles in the grid, the model is not available to any end user, and a notification says so.

Important: A newly created model starts with the toggle On and no roles, so it is not available to any user until you add roles or turn the toggle off.

This tab edits role membership only. Usage limits belong to the role; set them in Governance.

Add a role​

You can add a role only if the Make available to specific roles toggle is On.

  1. Click + Add (top-right of the Roles grid).
  2. Select one or more roles in the modal. The list of roles is defined in the Governance section.
  3. Confirm to add role(s) to the table.

Remove a role​

You can remove a role only if the Make available to specific roles toggle is On.

  1. Click the actions menu in the role's row.
  2. Choose Remove in the menu.

Interceptors​

DIAL uses interceptors to add custom logic to inbound and outbound requests for models and applications, enabling PII obfuscation, guardrails, safety checks, and more.

Note

Refer to Interceptors to learn more.

In the Interceptors tab, you can view configured global interceptors and define local interceptors that will be triggered for the selected model. You can define interceptors in the Governance section to add them to the processing pipeline of DIAL Core.

Add an interceptor​

Follow these steps to attach one or more interceptors to the model's configuration:

  1. Click + Add (in the upper-right of the interceptors grid).
  2. In the Add Interceptors modal, choose one or more from the grid of defined interceptors.
  3. Click Apply to append them to the bottom of the list (added in the same order as selected in the modal).

Tip

If you need a new interceptor, first create it under Governance and then revisit this tab to attach it to the model's configuration.

Reorder interceptors​

  1. Drag and drop the handle (⋮⋮⋮⋮) to reassign the order in which interceptors are triggered.
  2. Release to reposition; order renumbers automatically.
  3. Click Save to lock in the new execution sequence.

Remove an interceptor​

  1. Click the actions menu in the interceptor's row.
  2. Choose Remove to detach it from this model.
  3. Click Save to lock in the interceptors list.

Audit​

In the Audit tab, you monitor usage, cost and performance for the selected AI model. It has two sub-sections: Dashboard and Traces. The tab is shown only when the dashboard feature and the DIAL Admin API are enabled; otherwise the model has the Properties, Features, Catalog metadata, Roles and Interceptors tabs only.

Dashboard​

The Dashboard presents usage, cost, and performance analytics for the selected model over a chosen time range. When Analytics Dashboards (ANALYTICS_USAGE_ENABLED) are enabled, it reads DIAL Analytics. Otherwise Admin shows the legacy telemetry dashboard, which Admin Backend serves from the InfluxDB that the legacy Analytics Realtime service writes.

JSON editor​

Advanced users with technical expertise can work with the model properties in a JSON editor view mode. It is useful for advanced scenarios of bulk updates, copy/paste between environments, or tweaking settings not exposed on UI.

Tip

You can switch between UI and JSON only if there are no unsaved changes.

  1. Navigate to Models, then select the model you want to edit.
  2. Click the JSON Editor toggle (top-right). The UI reveals the raw JSON.
  3. Make changes and click Save to apply them.

Delete​
