DIAL RAG

DIAL RAG is an application that answers questions about the documents attached to a request. It indexes each document on first use, stores the index, and reuses it on later requests. This reference is for platform engineers who deploy DIAL RAG next to DIAL Core. To compare it with DIAL Generic RAG, see DIAL RAG or Generic RAG.

How it works​

  1. A request names documents. Documents are the attachments of every user message in the conversation, as DIAL file links or absolute URLs. A /attach <url> line in a message adds one more. DIAL Core forwards the request with a per-request key.
  2. DIAL RAG checks access. For a DIAL file, it reads the file's metadata through DIAL Core, which fails when the caller has no access. For an absolute URL, it sends a HEAD request.
  3. It loads or builds the index. It reuses a stored index when its settings match and the document hasn't changed. Otherwise it indexes the document and stores the new index. See Index storage.
  4. It forms the search query. In a conversation with more than one user message, the query model rewrites the latest question into a standalone one. Otherwise the latest message is the query.
  5. It retrieves chunks. When all chunks of the documents fit in about 12,000 characters, it uses all of them. Otherwise each retriever returns its 7 best chunks, and an equal-weight ensemble merges the lists.
  6. It answers. It sends the chunks and up to 4 page images to the chat model and streams the answer. Each cited chunk is attached to the response, with a page link for PDF documents.

DIAL RAG reports each step as a stage of the response. A request can also stop after indexing or after retrieval; see DIAL RAG API.

Retrievers​

Retriever, as its stage is namedWhat it searchesWhen it runs
Keywords searchChunk text, with BM25Always
Embeddings searchChunk text, embedded with epam/bge-small-en inside the containerAlways
Page image searchDescriptions of page images, written by a vision model and embedded with epam/bge-small-enWhen description_index is set, which is the default
Multimodal searchPage images, embedded with a multimodal embeddings modelWhen multimodal_index is set. It's unset by default.

The vision model and the multimodal embeddings model are deployments in DIAL Core. DIAL RAG plans their calls against the caller's token limits for that model. It reserves the expected tokens from the daily limit and paces requests to the minute limit. See Indexing.

Documents​

InputHow DIAL RAG reads it
PDFText, split into chunks of up to 1,000 characters by the unstructured library, and the page images
DOC, DOCX, ODT, PPT, PPTX, PPTM, ODPConverted to PDF with LibreOffice first, then read as PDF
Images (image/*)No text. The image is searched by the image retrievers and passed to the chat model.
Text formats, such as plain text and code filesText only, through unstructured

A PDF page without a text layer has no text chunks, because DIAL RAG doesn't run OCR. The image retrievers can still find it. A document whose extracted text exceeds 5 MiB is rejected (max_document_text_size).

Index storage​

Each index is one file of MIME type application/x.aidial-rag.index.v0. By default it goes to files/<DIAL RAG bucket>/dial-rag-index/<path>/index.bin. The path is the SHA-256 hash of the document's link, split into 8-character folders.

DIAL_RAG__INDEX_STORAGE__USE_DIAL_FILE_STORAGEWhere indexes live
False, the image's defaultOnly in an in-memory cache of 128 MiB per process. Indexes are lost on restart and not shared between replicas.
TrueIn DIAL file storage, with the in-memory cache in front

DIAL RAG reuses a stored index only when all of these hold:

  • Same index settings. The chunk size and the multimodal embeddings model are the same. The same image retrievers are turned on.
  • Same document. A DIAL file has the same ETag. A document outside DIAL has the same ETag and Last-Modified header.
  • Supported format. DIAL RAG migrates an older index format and saves it back, unless a request turns that off.

A client can also choose where an index is stored, for example in its own appdata folder. See Index attachments.

DIAL RAG or Generic RAG​

The two services don't depend on each other. Generic RAG's page_description transform describes page images in the same structure as DIAL RAG: a summary and a key fact for the page, and for each image and table on it. Both run the epam/bge-small-en embeddings model.

Deployed asOne applicationAn application type, with one application per document collection

Dependencies​

DependencyPurpose
DIAL CoreRoutes requests to DIAL RAG, issues per-request keys, stores documents and index files, and serves the models
A chat modelWrites the answer. With page images in use, it must accept images.
A query modelRewrites follow-up questions. It must support tool calling while use_history is on.
A vision model or a multimodal embeddings modelIndexes page images, for the image retrievers

DIAL Core must let the callers of DIAL RAG use these models, because DIAL RAG calls them with the caller's per-request key.

Warning

DIAL RAG downloads every absolute URL that a request attaches or names with /attach, from inside your network and without credentials. Limit its egress when internal endpoints must stay unreachable.
