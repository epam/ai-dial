DIAL Scheduler configuration

This reference covers Scheduler configuration for platform engineers deploying the API and worker beside DIAL Core. It assumes the service dependencies are available. Per-schedule triggers, target properties, and retries are described in API.

Configuration sources​

Defaults come from settings.py, the entrypoint, and the API scheduler factory. Settings classes read .env; process environment variables take precedence. Configuration is loaded at startup and cached.

The upstream README lists SCHEDULER_APP_ID=dial_scheduler, but code defaults to public/dial_scheduler__1.0.0. It describes sign-in checks as OBO probes; the implementation instead reads application auth status. The code also includes DB_SCHEMA, ENV, and CLIENT_CHANNEL_SIGNIN_TIMEOUT_SECONDS, which its environment tables omit.

Database connection and pool​

The API and worker must share the same PostgreSQL database and schema. Supply database settings to the migration container as well. The online migration path initializes the shared database engine, which also loads the required DIAL settings.

In connection-string mode, the async engine uses DB_URL; the job store rewrites its driver to postgresql+psycopg2. Sources: database settings and validation, URL selection, async engine, job-store engine, and migrations.

DB_GCP_PRIVATE_IPfalseSelect the Cloud SQL private IP connection.

All three workload identity modes reject a configured DB_PASSWORD or DB_URL. The workload must have the cloud identity, network access, and database permissions required for the selected mode. Missing mode-specific settings fail validation at startup. See credential providers and mode validation.

Worker and job settings​

VariableDefaultDescription
NOOP_INTERVAL_SECONDS60Worker heartbeat interval, in seconds.
JOB_COALESCEfalseWorker fallback for combining multiple missed fires into one.
JOB_MAX_INSTANCES1Worker fallback for concurrent instances of the same timed job.
JOB_MISFIRE_GRACE_TIME60Worker fallback grace period after a scheduled fire, in seconds.

The worker reads these JOB_* settings, but the API registers jobs with fixed defaults: coalesce=false, max_instances=1, and misfire_grace_time=60. Those values are stored with the job. Changing worker variables alone does not override defaults already assigned by the API. Immediate runs use the API's background launcher and can overlap an existing run.

Sources: worker creation, API job defaults, and immediate runs.

Health settings​

VariableDefaultDescription
READINESS_DB_TIMEOUT_SECONDS2.0Database check timeout, in seconds, for API and worker readiness.
WORKER_HEALTH_DIR/tmpDirectory for started, heartbeat, and ready marker files. Must be writable.

NOOP_INTERVAL_SECONDS must stay below the liveness probe's staleness threshold. Kubernetes worker probes check marker existence and heartbeat age with exec; HTTP probes apply only to the API. See probe configuration.

The two prefixes have identical defaults. API_HTTP_* controls the API client and immediate runs; WORKER_HTTP_* controls timed runs.

API_HTTP_IDLE_TIMEOUT_SECONDS, WORKER_HTTP_IDLE_TIMEOUT_SECONDS60.0Maximum gap between parsed stream events, in seconds; heartbeat pings do not reset it.

A schedule's properties.timeout and properties.idle_timeout override the corresponding process defaults. The duration ceiling applies separately to each attempt. Scheduler's retry policy does not retry duration expiry, stream inactivity, or transport failures without an HTTP status. See HTTP defaults, retry execution, and executor timeouts.

Register Scheduler in DIAL​

The upstream application definition registers an asset application with path public/dial_scheduler__1.0.0.

  1. Create a Scheduler project key in DIAL Admin under Governance > Keys, and assign it a role with access to the Scheduler application.
  2. Set DIAL_API_KEY in API and worker to that key. Set the application's app_identity to its SHA-256 hash.
  3. Import the application definition under AI Gateway > Applications; see Import. Replace both <SCHEDULER_URL> occurrences with the API service URL, such as http://scheduler-api:5000.
  4. Retain the main application route with rewritePath=true and its upstream pointing to the API. The MCP definition points to <SCHEDULER_URL>/mcp, with HTTP transport and forwardPerRequestKey=true.
  5. Retain external_services.dial-native.auth_settings.authentication_type=DIAL_NATIVE. In the application's External Services, open DIAL Native and click Grant consent.
  6. Set SCHEDULER_APP_ID=public/dial_scheduler__1.0.0 in API and worker, or use the actual resource path if the imported asset differs.
  7. Each user enables offline access through DIAL Chat's Extensions. Check sign-in status before creating a schedule.

Scheduler requires DIAL Core 0.47.0 or later, the first release with DIAL_NATIVE external services, the /v1/user/offline-credentials endpoint, and the /v1/ops/external-service/obo-credentials operation. For a DIAL_NATIVE service, that operation redeems the owner's offline credentials, which Core obtains through the identity provider's offline client. The upstream local Core sample provides integration context.

Administrator consent applies to the application across users who enabled offline access. User sign-out prevents that user's later runs; withdrawing administrator consent prevents the application's later delegated runs. The service key obtains credentials for the owner; it is not the target request's user identity. See credential resolution.

Warning

A schedule supplies its target URL, and execution sends delegated credentials to that target. Limit target network access to trusted services and protect the database containing payloads and results.

Deployment example​

The following Compose fragment assumes an existing PostgreSQL service named postgres and Core service named dial-core on the same network. The scheduler database and user must already exist, and PostgreSQL must be ready before migrations start. Docker Hub publishes only the development tag; there is no image for release 0.3.1. Supply a Docker Hub image tag as SCHEDULER_IMAGE_TAG, or replace image with one built from the 0.3.1 Dockerfile. Supply SCHEDULER_DB_PASSWORD and SCHEDULER_API_KEY through the deployment's environment.

x-scheduler: &scheduler
  image: epam/ai-dial-scheduler:${SCHEDULER_IMAGE_TAG:?Set the Scheduler image tag}
  platform: linux/amd64
  environment: &scheduler-environment
    DIAL_URL: http://dial-core:8080
    DIAL_API_KEY: ${SCHEDULER_API_KEY:?Set the Scheduler project key}
    SCHEDULER_APP_ID: public/dial_scheduler__1.0.0
    DB_AUTH_MODE: password
    DB_HOST: postgres
    DB_NAME: scheduler
    DB_USER: scheduler
    DB_PASSWORD: ${SCHEDULER_DB_PASSWORD:?Set the database password}

services:
  scheduler-migrations:
    <<: *scheduler
    environment:
      <<: *scheduler-environment
      SERVICE: migrations
    restart: "no"

  scheduler-api:
    <<: *scheduler
    environment:
      <<: *scheduler-environment
      SERVICE: api
    depends_on:
      scheduler-migrations:
        condition: service_completed_successfully
    expose: ["5000"]

  scheduler-worker:
    <<: *scheduler
    environment:
      <<: *scheduler-environment
      SERVICE: worker
    depends_on:
      scheduler-migrations:
        condition: service_completed_successfully

This fragment adds the three Scheduler processes to an existing deployment; it does not register the application or configure offline delegation. The upstream Compose file includes a PostgreSQL service and migration ordering.

Connect DIAL Chat​

The Chat feature settings control the user interface and BFF routes:

SCHEDULED_TASKS_ENABLED=true
SCHEDULER_APP_ID=public/dial_scheduler__1.0.0
SCHEDULER_SERVICE_ID=dial-native

Chat's SCHEDULER_APP_ID must match Scheduler's application resource path; SCHEDULER_SERVICE_ID names its registered external service. SCHEDULER_SERVICE_TIMEOUT_MS defaults to 10000; this Chat-to-Scheduler request timeout is separate from target execution timeouts. Restart Chat after changing its environment.

Check that Scheduled tasks appears, complete offline sign-in, and create a task targeting an available model. Start now should create a run whose status eventually becomes success and whose result appears as a conversation. A successful immediate run verifies the API execution path; allow the next timed fire to verify the worker as well.

Troubleshooting​

SymptomWhat to check
Startup rejects database settingsRequired values for DB_AUTH_MODE; remove DB_PASSWORD and DB_URL in workload identity modes.
Chat returns 503 for scheduled-task callsChat's application ID; create and update also need its service ID.
Create or replace returns 403The owner's offline sign-in for the requested service.
Create or replace returns 502 with state=unknownAdministrator consent, application path, external-service registration, Core reachability, and auth-status response fields.
Run fails with result.stage=credentialsApplication identity, Scheduler project key, administrator consent, and the owner's current offline credentials. The target was not dispatched.
Immediate runs work but timed runs do notWorker startup and readiness, shared database/schema, and job-store connectivity.
Duplicate timed executionsMore than one worker or overlapping workers during a rollout.
Worker restarts repeatedlyWritable health directory; heartbeat interval below the probe's staleness threshold.
Changing JOB_* has no effectThe API stores its own fixed defaults with each job.
Successful run has no conversationOnly chat completions with create_conversation=true qualify. Check conversation_create_failed logs; storage failure does not fail the run.
