Manage applications

An application or agent in DIAL is a service that DIAL Core serves to clients alongside models and toolsets. Clients call it by name. DIAL Core applies the same access control, interceptors, limits, load balancing and logging as for models.

You register an application by telling DIAL Core how to reach it. There are four ways:

  • Interfaces. Declare the OpenAI Chat Completions interface of the application and serve it from a base URL. Alternatively, the interface can be served by a translator, so the application serves an API it doesn't implement itself.
  • Endpoints. Point DIAL Core directly at an external service: a Chat endpoint (and an optional Responses endpoint for the OpenAI Responses API), an MCP endpoint, or both.
  • Application runner. Select an application runner, such as Quick Apps, Code Apps or a custom runner. DIAL Core forwards requests to the endpoints defined in the runner's configuration, and users create configured instances from it.
  • Application container. Deploy the application as a container in DIAL and create the application from the running container. See Application containers. Applications created this way appear under Entities, which is being deprecated.

You can also add applications by editing the DIAL Core configuration, through the DIAL Core API, or when users publish them. This page describes how administrators add and configure applications in DIAL Admin.

Note

  • Refer to DIAL-Native Applications to learn about applications in DIAL.
  • Refer to Enable App to learn how to enable applications in DIAL.

Main screen​

On this screen, you can access all the available application deployments in your instance of DIAL. Applications displayed in this section were either added by direct modification of the DIAL Core config file, via DIAL Admin, DIAL Core API or published by users. Here, you can also create and manage new application deployments.

Folders​

The tree has three top-level (root) folders. Click a folder to list its contents in the grid.

Root folderWhat it is and how it behaves
fileApplications defined in the DIAL Core configuration files (as opposed to the database/API-managed assets in the other buckets). A read-only, names-only listing: no Create button and no row, bulk, or folder actions. Opening an entry shows its configuration in read-only mode, marked with a READ ONLY badge; it cannot be edited, deleted, duplicated, or moved. Use this to see which applications come from the static config rather than from published assets.
platformApplications stored in DIAL Core platform blob storage. This is where you create, edit and delete applications in DIAL Admin. It also adds a Roles section on the configuration screen (see Roles). Appears when the Catalog menu group is enabled.
publicA public bucket. Applications get here when published by users or added by administrators.

The grid columns, the Create menu, and the available row actions all change depending on which bucket you are browsing.

Create: Folder, Application, or Import​

The Create dropdown in the header is the single entry point for adding content. Its items depend on the bucket:

  • Public bucket:
    • Folder — adds a new folder in the tree.
    • Application — opens the Create Application modal.
    • Import — opens the Import modal.
  • Platform bucket: only Application.
  • File bucket: no Create button (read-only).

Create​

  1. Select the target folder, click Create, and select Application.

  2. Fill in the required form fields:

    FieldRequiredDescription
    IDYesUnique identifier of the application.
    Display NameYesName shown on the UI (e.g. "Customer Support Bot").
    VersionYesSemantic version (e.g. 1.0.0, pre-filled). Hidden when creating in the platform bucket.
    DescriptionNoFree-text description of the application.

  3. Click Next to navigate to the Source Type screen:

    • Interfaces - select among the supported interfaces.
    • Endpoints — two independent checkboxes (at least one must stay checked):
      • Chat Endpoint → Completion endpoint (required; processes chat completion requests) and Responses endpoint (optional; processes OpenAI Responses API calls).
      • MCP Endpoint → Endpoint (required), Transport (fixed to HTTP), Forward per request key (toggle; forwards a per-request key so the MCP server can reach DIAL storage), Configuration delivery (Header or Meta—how the app's configuration is delivered to the MCP server).
    • App Runner — a single Select Application Runner dropdown. The runner acts as a factory; DIAL Core forwards payloads to the endpoints defined in the Application Runner configuration.
    • Code App — a read-only Editor URL (pre-filled from the configured code-app editor); nothing else to enter.

  4. Click Create. The dialog closes and the new application configuration screen opens. The entry appears immediately under the selected folder.

Tip

You can quickly add applications by duplicating an existing one—use Duplicate in its row menu, then choose New Version or New Application.

Export​

You can export individual applications or whole folders (including nested folders).

  • To export a folder or application, choose Export in its row actions menu.
  • To export several items at once, select them and use Export in the bulk-actions toolbar.
  • In the Export dialog, choose the Format: DIAL Admin Archive or JSON.

Import​

Importing lets you migrate, restore, or share application assets between DIAL instances.

  1. Click Create and select Import.
  2. On the Files step, choose the file type and add your files (drag and drop or Browse):
    • DIAL Admin Archive — a single aidial-admin.zip archive (one at a time, max 4 MB).
    • DIAL Core JSON Files — up to 30 JSON files, max 4 MB per file and 64 MB in total.
  3. Optionally enable Ignore paths to disregard the folder structure stored in the files (everything imports into the current folder).
  4. On the Properties step, choose a Conflict resolution strategy:
    • Skip — keep existing applications; add only new ones.
    • Override — replace applications that have the same name and version.
  5. Review the preview—items with validation errors or conflicts are flagged before import.
  6. Click Finish.

Configuration​

Click any application to open its configuration screen. At the top of the Properties tab, a header band shows Updated Time, Creation Time, and Folder Storage (the folder path, with a link that opens it in Folders Storage on public applications; platform without a link on platform applications).

Top bar controls

ControlDescription
VersionDropdown to view and edit a specific version, or create a new one. Enabled in the public folder.
DeleteDelete the selected application.
JSON Editor (toggle)Switch between the form UI and the raw JSON view.
Save / Save as new version / DiscardAppear when there are unsaved changes. Save updates the current version; Save as new version stores the edits as a new version; Discard reverts them (with confirmation).

The screen is organized into sections: Properties, Features, Parameters, Catalog metadata, Interceptors, Dependencies, and App Routes. Conditional sections:

  • Tools Overview appears only when the application exposes an MCP endpoint (its own, or from its Application Runner).
  • Roles appears only for applications in the platform and file buckets.
  • Audit appears when Analytics Dashboards (ANALYTICS_USAGE_ENABLED) are enabled. It contains the usage Dashboard only.

Applications opened from the file bucket are read-only (a READ ONLY badge appears and the action buttons are hidden).

Source Types​

Interfaces

Applications can declare the OpenAI Chat Completions interface. To set the OpenAI Responses API, use the Responses endpoint under Endpoints.

When provided, DIAL Core forwards each request to that base URL followed by the path the request arrived on. An interface listed without a base URL of its own uses the app-level Base URL. If neither is set, requests to that interface fail with HTTP 503.

FieldRequiredDescription
Base URLOptionalThe root URL that the matching ingress path is appended to. The app-level Base URL serves an entry that omits it.
ModeNoPassthrough (default) or translator. It declares whether the request is forwarded in the shape it arrived in, or handed to a translator that converts it into an API the application does serve. A translator interface does not touch the caller's role limits — neither checks nor charges them. The translator calls DIAL Core back to have the completion served, and that second call is the real request: it carries the tokens, the cost and the requestHour/requestDay slot, so a client call is counted once rather than twice. An exhausted quota is therefore enforced on the callback rather than on the translated call itself.
TranslatorOptionalThe translator serving this interface, required by mode: translator and rejected without it. An interface is served either by a base URL or by a translator, never by both — an application declaring both is rejected on config load.
Default HeadersNoHeaders applied to requests for this interface only, laid over the app-level Default Headers.
FeaturesNoFeature fields that override app-level features for this interface only. Unspecified fields inherit the app-level value, then Core defaults apply.
DefaultsNoBody parameters applied to requests for this interface only, replacing whichever app-level defaults would otherwise serve it. They are injected the same way the app-level ones are — a key the request already carries is never replaced.
Override PathsNoPer-operation upstream paths that replace the default "base URL + ingress path" routing for this interface.

Refer to DIAL Core documentation to learn more about interfaces, how to configure them and how they work.

Endpoints

Application with this source type is a standalone application. DIAL Core communicates with it via the explicitly-provided chat completion, responses, and/or MCP endpoints.

  • Chat Endpoint → Completion endpoint (required; processes chat completion requests) and Responses endpoint (optional; processes OpenAI Responses API calls).
  • MCP Endpoint → Endpoint (required), Transport (fixed to HTTP), Forward per request key (toggle; forwards a per-request key so the MCP server can reach DIAL storage), Configuration delivery (Header or Meta—how the app's configuration is delivered to the MCP server).
  • Viewer URL — URL of a custom end-user UI; when set, it overrides the standard DIAL Chat UI for this application.
  • Editor URL — URL of a custom UI for configuring the application.

App Runner

Application runners can be seen as application factories, allowing users to create logical instances of apps with different configurations. Application runners are based on JSON schemas, which define structure, properties, and endpoints for applications. Select one of the available application runners. If the application is created based on an application runner, DIAL Core will forward all payloads to endpoints defined in the application runner configuration.

Code App

A single read-only Editor URL (the configured code-app editor).

External Services​

External services the application authenticates to.

  • Service ID: Service identifier.
  • Display Name: Service name.
  • Description: Service description.
  • Authentication parameters: OAuth setting provided by the IDP provider or API key.

Refer to Toolsets Authentication for fields description.

Tools overview​

Important

This section is enabled for application deployments with Source Type = Endpoints/MCP or Source Type = Application Runner where the related Application Runner has the MCP endpoint enabled as the source type.

Tools are functions supported by an MCP server that can be used by clients to perform specific actions. On this screen, you can discover, manage, and try all the available tools.

Note

Refer to Toolsets — Tools overview to learn more about the purpose and functionality of this section.

Features​

Control the application's optional capabilities. Values set on an Application Runner are inherited by applications built from it (shown with a "This value is inherited from Application Runner features" tooltip); setting them here overrides the runner.

The difference between model and application features​

While model feature flags govern what each AI model integration can do, application feature flags define which of those capabilities your orchestrated service exposes to clients. You can also plug in custom preprocessing endpoints.

Scope

  • Model features apply per AI model, controlling what the model endpoint itself supports (e.g. whether GPT-4 can accept system prompts or function calls).
  • Application features apply per orchestrated service, governing what your composed workflow will accept and pass through — regardless of which models are called under the hood.

Override capability

  • At the application level, you can disable a feature globally (even if models support it) or plug in custom endpoints that apply above all models.
  • At the model level, toggles only reflect the true capabilities of that specific AI model integration.

Use cases

  • Model toggles ensure you don't accidentally send unsupported parameters to a given model.
  • Application toggles let you present a consistent API to your clients (e.g. always accept temperature or never allow attachments), even if different underlying models behave differently.

Endpoints​

Service endpoints — optional URLs that extend the app's runtime behavior:

FieldDescription
Rate endpointA custom rate-estimation API to compute cost or quota usage (e.g. per-tenant or complex billing).
Tokenize endpointA custom tokenization service for precise, app-wide token counting.
Truncate prompt endpointYour own prompt-truncation API for advanced context-window management.
Configuration endpointA URL returning a JSON Schema of the application's settings. DIAL Core exposes it as GET v1/deployments/<deployment name>/configuration.

Reasoning​

Reasoning Efforts defines the reasoning effort levels the apps supports (e.g. low, medium, high). When configured, DIAL Chat displays a selector that lets users choose a reasoning effort for each request. Leave empty if the model does not support reasoning effort control.

Other Capabilities​

Capability toggles. Each toggle tells DIAL (and clients) that the application supports a given request parameter or capability; when off, DIAL treats that feature as unavailable for the app.

By default, DIAL Core treats the following features as enabled: System prompt, Parallel tool calls, Max tokens, Custom temperature, Allow resume and Accessible by request key. The Temperature supported, Seed, Max completion tokens, Tools, Skills, Content parts, URL Attachments, Folder Attachments and Assistant Attachments in request toggles are disabled by default, and no Reasoning Efforts are set. The toggles are grouped by purpose:

GroupToggleWhat it controls
Sampling & Output ControlTemperature supportedThe app accepts temperature, which controls output randomness (lower = more deterministic, higher = more varied). Enable only if the underlying model honors it.
Custom temperatureThe app allows a custom temperature value instead of forcing a fixed/default one.
SeedThe app accepts seed, so the same seed and inputs reproduce the same output—useful for testing and reproducibility.
Max tokensThe app accepts max_tokens, capping the length of the generated completion.
Max completion tokensThe app accepts max_completion_tokens, the newer cap on completion length used by reasoning-style models.
Tools / Function CallingToolsThe app accepts tools/functions, letting the model call external functions you define in the request (e.g. calendar lookup, DB fetch).
Parallel tool callsThe app accepts parallel_tool_calls, letting the model request several tool calls in one turn.
SkillsThe app supports skills.
Prompt & Message CompositionSystem promptThe app accepts a system message that sets the assistant's role and instructions—useful for agent orchestration.
Content partsThe app accepts multi-part message content (e.g. text plus images in one message) rather than plain text only.
AttachmentsURL AttachmentsThe app accepts attachments referenced by URL instead of uploaded files.
Folder AttachmentsThe app accepts a whole folder as an attachment, batching its files in one request.
Assistant Attachments in requestDIAL keeps attachments on prior role=assistant messages when sending the conversation back, so the app can reuse files it generated earlier. See chat completion requests.
Session & AccessAllow resumeThe app supports resuming a previously interrupted generation instead of restarting it.
Accessible by request keyThe app can be invoked with a per-request API key, which is how one deployment calls another on a user's behalf.
Consent requiredUsers must grant consent before they can use the app the first time.
FeedbackSupport comment in rate responseThe app's rate endpoint can return a free-text comment alongside the numeric score.

Parameters​

For applications built from an Application Runner, this section configures the parameters defined by the runner's schema. Use the View selector to choose how parameters are presented:

  • Table — the parameters as a grid.
  • Generated form — a form generated from the runner's JSON schema.
  • Application custom UI — the application's own configuration UI, embedded from its editor URL.

Note

Refer to Schema-rich Applications to learn more.

Catalog metadata​

Catalog metadata holds the values for the fields of the catalog schema attached to the application. The section is empty until you select a schema in the Catalog schema field on Properties:

  • No schema selected — the section shows "Select a catalog schema on the Properties tab to edit its catalog metadata."
  • Schema selected — the schema's fields render for you to complete. Use the View selector to switch between a generated Form and raw JSON. A banner flags any stored properties the schema does not declare.

Roles​

Roles tab appears only for applications in the platform and file buckets.

In the Roles tab, you define which roles can call the application. This tab edits role membership only. Roles and their usage limits are defined in the Governance section.

Note

  • Refer to Access & Cost Control to learn more about access control in DIAL.
  • Refer to Roles to learn more about roles in DIAL.
  • Refer to tutorials to learn how to configure access and limits for JWT and API keys.

Roles grid​

ColumnDescription
Display NameUnique role name displayed on UI.
DescriptionDescription of the role's purpose (e.g., "DIAL Prompt Engineering Team").

Role-specific access​

Use the Make available to specific roles toggle to define access to the application:

  • Off: Application is callable by any authenticated user. The grid lists all roles and is read-only.
  • On: Application is restricted — only the roles you explicitly add to the grid can call it. With no roles in the grid, the application is not available to any end user, and a notification says so.

Important: A newly created platform application starts with the toggle On and no roles, so it is not available to any user until you add roles or turn the toggle off.

Add a role​

You can add a role only if the Make available to specific roles toggle is On.

  1. Click + Add (top-right of the Roles grid).
  2. Select one or more roles in the modal. The list of roles is defined in the Governance section.
  3. Confirm to add role(s) to the table.

Interceptors​

DIAL uses interceptors to add custom logic to inbound and outbound requests for models and applications, enabling PII obfuscation, guardrails, safety checks, and more.

You can define interceptors in the Governance section to add them to the processing pipeline of DIAL Core.

Note

Refer to Interceptors to learn more.

The section is split into collapsible groups, each showing its count:

  • Global Interceptors — read-only. Interceptors from System Properties that apply to all deployments.
  • Runner Interceptors — read-only. Inherited from the application's Application Runner. Shown only when the app has a runner source.
  • Local Interceptors — editable. The application's own interceptors. Use + Add to attach them, drag to reorder, and remove them from the row menu.

Request interceptors run in the listed order; response interceptors run in reverse. Each group's grid shows Display Name and Description.

The difference between model and application interceptors​

Scope of invocation

  • Model: Interceptors are triggered with each request to a model (i.e. before/after the LLM invocation).
  • Application: Interceptors wrap the entire orchestrated workflow, including multi-model sequences and branching logic.

Use cases

  • Model: Ideal for prompt pre-processing or response transformations that are specific to each LLM.
  • Application: Manage cross-cutting concerns across the whole application (e.g., tenant-based routing, unified logging, end-to-end policy enforcement).

Interceptors grid​

ColumnDescription
OrderExecution sequence. Interceptors run in ascending order (1 → 2 → 3...). A request will flow through each interceptor in this order. Response interceptors are invoked in the reversed order.
Display NameThe interceptor's alias, matching the Name field in its definition.
DescriptionFree-text summary from the interceptor's definition, explaining its purpose.
IDUnique identifier of the interceptor.
ActionsAdditional interceptor-specific actions: open interceptor in a new tab, or Remove the selected interceptor from the app's configuration.

Add an interceptor​

  1. Click + Add (in the upper-right of the interceptors grid).
  2. In the Add Interceptors modal, choose one or more from the grid of defined interceptors.
  3. Click Apply to append them to the bottom of the list (added in the same order as selected in the modal).

Tip

If you need a new interceptor, first create it in the Governance section and then revisit this tab to attach it to the application's configuration.

Reorder interceptors​

  1. Drag and drop the handle (⋮⋮⋮⋮) to reassign the order in which interceptors are triggered.
  2. Release to reposition; order renumbers automatically.
  3. Click Save to lock in the new execution sequence.

Remove an interceptor​

  1. Click the actions menu in the interceptor's row.
  2. Choose Remove to detach it from this application.
  3. Click Save to lock in the interceptors list.

Dependencies​

In interconnected systems, applications often rely on other applications or AI models to function, forming complex dependency chains. Access to sensitive data in such ecosystems can pose a challenge, especially when multiple applications interact and propagate requests, and may require explicit consent from a user to allow an application or AI model to access their data or perform actions on their behalf.

Note

Refer to Managing Authorization in Complex Application Ecosystems to learn more.

On this screen, you can find all dependencies configured for the selected application. Administrators can manually add new dependencies (by selecting from available AI models and applications) or remove the existing ones.

ColumnDescription
Entity TypeIndicates whether the dependent object is an Application or a Model.
IDIdentifier of the respective model or application.
Display NameDescriptive name of the dependent model or application.
VersionVersion of the dependent model or application.
DescriptionAdditional textual details about the dependent model or application.
ActionsAllows opening the dependent object in a new tab or removing it from the list of dependencies.

Add a dependency​

  1. Click + Add (in the upper-right of the dependencies grid).
  2. Select the type of object to add: Application or Model.
  3. In the modal window, choose a model or application existing in DIAL from the grid.
  4. Click Add to append them to the dependencies grid.

App Routes​

Define and manage routes that DIAL Core uses when interacting with this application via specified endpoints. The left panel lists the routes; click + Add and enter a Display Name to create one. Route configuration mirrors Routes.

Each route is configured through three sections:

  • Properties — Display Name, Paths, Rewrite path (toggle), Methods, Output (Upstreams or Response), Upstream Endpoints (with Weight and Tier), Max retry attempts, Permissions, and Order.
  • Attachments — Request attachment paths and Response attachment paths.
  • Roles — the Inherit Application Roles toggle and a Roles grid (when inheritance is off).

Audit​

In the Audit tab, you monitor usage, cost and performance for the selected application. For these applications it contains the Dashboard only. The tab is shown when Analytics Dashboards (ANALYTICS_USAGE_ENABLED) are enabled, and its Dashboard reads DIAL Analytics.

The Dashboard presents usage, cost, and performance analytics for the selected application over a chosen time range.

JSON editor​

Advanced users with technical expertise can work with the application properties in a JSON editor view mode. It is useful for advanced scenarios of bulk updates, copy/paste between environments, or tweaking settings not exposed on UI.

Tip

You can switch between UI and JSON only if there are no unsaved changes.

  1. Navigate to Applications, then select the application you want to edit.
  2. Click the JSON Editor toggle (top-right). The UI reveals the raw JSON.
  3. Make changes and click Save to apply them.

Delete​

  • Click Delete on the Configuration screen toolbar.
  • Use Delete in the application's row actions menu.
  • Delete the folder that contains the application.
  • Select applications on the main screen and use the bulk-actions Delete.

Warning

Deleting an application is permanent. Applications that depend on it will stop working.
