Request flow

Requests routed through DIAL enter DIAL Core. Core authenticates the caller, checks access, and forwards the call to its configured target. This page explains the main runtime paths for architects who have read Architecture highlights.

The four request paths​

A client can be DIAL Chat, a coding agent, an automation tool, your own software, or another DIAL application. The target determines both the protocol and what Core does after authorization. A model invocation, an MCP tool call, and a proxied HTTP request are distinct operations even when they share the same gateway.

note

This is a logical map, not a deployment topology. Adapters are needed for provider-specific integration; a compatible endpoint can be configured directly. An application becomes a client when it calls another model, application, or tool through Core.

Models​

Core resolves the requested model deployment and selects its configured API path and upstream. An adapter handles provider authentication and either converts the provider format or preserves it in passthrough mode. The client therefore integrates with the exposed interface rather than managing every provider's credentials and transport.

info

Provider connectivity does not mean every client API is supported. Responses currently uses only the Azure OpenAI Adapter. Anthropic Messages supports passthrough across all adapters for compatible models, plus translation through Chat Completions inside the Bedrock Adapter. Responses-based translation is planned. See API support and supported providers.

Applications​

Core invokes a registered application directly through its endpoint; an application does not need a model adapter in front of it. An application serves the APIs it declares: Unified API chat completions, and optionally OpenAI Responses or Anthropic Messages. A model's support for an API does not make an application accept it.

An application often needs several model or tool calls to answer one request. In the sequence below, it calls back through the same Core service. The second interaction is a delegated call, not a second required gateway deployment.

The target may be reached through an adapter or MCP server; those hops are omitted here. A per-request key carries the caller's context and is invalidated when its request completes. Applications with sensitive dependencies can also require user consent.

Delegation lets Core check the user's context for nested calls and associate them with the originating work. It does not give the application unrestricted access to every resource. The per-request key reference describes file access and credential lifetime.

warning

Applications can also have direct network connections. Core governs calls made through it; external data access depends on the application's own credentials and network permissions. See Application hosting and lifecycle for the hosting and operating boundary.

MCP toolsets​

A Toolset gives an MCP client a governed endpoint in Core for an MCP server. The client can be an application or a coding agent. Core checks access and proxies tool discovery and execution; the MCP server implements the actual tools and connections to enterprise systems.

For example, an agent can discover a document-search tool and then call it through the same Toolset endpoint. The server's credentials determine what the external document system permits. Toolset credentials can be per-user or shared across the organization, so the downstream identity is an important design choice. See What is a Toolset.

Tool discovery is separate from the model deciding to call a tool. The application or agent coordinates those steps; a model API and MCP are not interchangeable transports.

Routes​

A route exposes a custom HTTP API through DIAL Core. Core matches the configured path and method, checks the caller's access, and forwards the call to the upstream service. Routes can also proxy WebSocket traffic.

Use a route to make an existing service available to DIAL clients under DIAL access control. The service keeps its own API, behavior, and data model. Route registration does not turn it into a model or an MCP server, and its external side effects still need application-level handling. See Manage routes and the route configuration reference.

Interceptor processing​

Interceptors inspect or modify requests and responses on supported model/application paths. They can implement redaction, content rules, or other cross-cutting processing without adding that logic to every application. Their scope determines which deployments use them.

Errors and incomplete work​

An invalid credential, denied permission, or exceeded limit can stop a request before forwarding. A successful authorization does not guarantee a successful provider or tool call: the target can reject the request, time out, or fail after output has started.

warning

Clients need to distinguish a rejected request from an interrupted stream. Replaying an application or tool call can repeat an external action, and a retry is not a guarantee that an earlier attempt did nothing. Exact retry and cancellation behavior must be established for the selected API and release.
